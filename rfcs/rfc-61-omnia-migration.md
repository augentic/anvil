# RFC-61: The In-Place Migration — Specify and its Adapters as Omnia Guests

> Status: Draft · Supersedes: the S1–S4 staging (RFC-51–54, RFC-56–59, and the implementation-sequence note — removed from the tree; recoverable from git history) · Defers: [RFC-55](future/rfc-55-working-tree.md) (distributed working trees), [RFC-60](future/rfc-60-verify-profiles.md) (verify profiles) · Owns: the end-to-end migration plan

## Abstract

Specify migrates **in place** from prose plus a Rust-native `specify` binary to a family of `wasm32-wasip2` components with the prose compiled in, hosted by the Omnia runtime. Control inverts: instead of a Cursor agent reading skill markdown and shelling out to `specify`, guest Rust code calls the `wasi-model` host (`omnia:model/completion.create`) and the bound cursor backend spawns `cursor-agent` against the mounted working tree; reference documents reach the spawned agent through an embedded MCP server each adapter guest serves over `wasi:http`. The specify-adapters ship as a collection of wasm components co-loaded by one Omnia deployment.

The inversion sorts every line of today's prose into one of three destinations: **orchestration prose becomes guest Rust** (workflow sequencing that skill markdown currently narrates compiles into deterministic control flow), **judgment prose becomes compiled-in prompt bodies** (briefs sent through `create`), and **reference prose becomes the MCP shelf** (fetched lazily by the spawned agent). The `/spec:*` skills survive only as ultrathin wrappers that invoke the `specify` CLI and relay its output — no workflow logic remains agent-side.

The earlier architecture RFCs (51–59) were drafted before the Omnia refactoring; much of what they specified now exists in a different, implemented shape. This RFC replaces their staging with a plan grounded in three anchors only: the migration intent above, what Omnia and the backends implement today, and [`wit/specify.wit`](../wit/specify.wit) as the adapter contract. Where an old RFC's mechanism was implemented, this RFC cites the implementation; where it was superseded, this RFC states the replacement; nothing here depends on unimplemented runtime capability except where explicitly called out as a constraint designed around.

## What the runtime already provides

The hosting side of the migration is largely built. The [`augentic/omnia`](https://github.com/augentic/omnia) and [`augentic/backends`](https://github.com/augentic/backends) repositories implement:

- **Multi-guest deployments.** One `omnia.toml` manifest declares `[[guest]]` entries (many wasm components on one `Engine` + shared `Linker`), `[[mount]]` filesystem preopens, `[[route.http]]` longest-prefix routing, and per-guest `link` allow-lists. Omnia's manifest tests already model a Specify-shaped layout (`workflow` + adapter guests with `link = ["augentic:specify/source", …]`).
- **Instance-per-call execution.** Every trigger, link dispatch, and host→guest callback instantiates a fresh instance from a pre-resolved `InstancePre` on a new `Store` and discards it.
- **Host-mediated guest-to-guest dispatch.** A guest imports an interface it does not satisfy; the manifest allow-lists it; the host polyfills the import over in-process wRPC and selects the target guest by the call's first string argument (`FirstArgSelector`) — exactly the `adapter-id`-as-data convention `specify.wit` assumes. Plain values only: resource handles cannot cross the seam.
- **The `wasi-model` host.** `omnia:model@0.1.0` exposes async `create(request) -> result<reply, error>` with chat-style messages, `format: text | json | schema(...)` (the host gate validates answers against the schema before the guest sees them), `tools` carrying MCP grants (`mcp { name, tools, url }`), and `grants` carrying `references` (a guest id for host→guest `resolve` dispatch), `workspace` (a lent `borrow<wasi:filesystem/descriptor>` the host resolves against the mount registry), and `verify` (accepted but stubbed).
- **The cursor model backend.** `omnia-cursor` implements `WasiModelCtx::complete`: it reads the host-resolved workspace `local_path`, merges MCP grants into `<workspace>/.cursor/mcp.json` (RAII guard, refcounted), spawns `cursor-agent --print --force --trust --output-format stream-json --workspace <path> [--approve-mcps] [--model <id>]`, parses the NDJSON stream, and retries once on an invalid answer. Each `create` is a fresh, context-free spawn; there is no session reuse.
- **The replay backend.** `ModelDefault` serves recorded answers from `MODEL_REPLAY_DIR`. It is a test-and-example convenience only — deterministic coverage of Specify's judgment legs lives in native core tests through the `Model` capability trait, not in a recorded-fixture pipeline.
- **The MCP guest SDK.** `omnia_guest::mcp` provides the `McpServer` trait and a path-agnostic JSON-RPC/Streamable-HTTP router served through `wasi:http/incoming-handler` — the docs-server pattern.
- **The composed example.** [`backends/examples/cursor`](https://github.com/augentic/backends/tree/main/examples/cursor) runs the full inverted loop today: a single component exports both `wasi:cli/run` (builds a `Request` with an MCP grant naming its own HTTP route and a `grants.workspace` lend of its `"."` preopen, calls `create`) and `wasi:http/incoming-handler` (serves the embedded MCP docs the spawned agent fetches), hosted by a `runtime!({ mode: command, hosts: { WasiHttp: HttpDefault, WasiModel: Cursor, … } })` binary whose HTTP trigger runs in the background while the CLI command drives.

What the migration builds is therefore almost entirely **guest-side**: the adapter components, the workflow component, the prose embedding, and the Specify deployment binary. The runtime constraints that shape the design are catalogued in [Constraints designed around](#constraints-designed-around), not treated as blockers.

## The target shape

The repository restructures to match the inversion. The Rust code in `engine/` moves to a root `src/` directory — the Rust workspace becomes the repository root — and the repo flips from prose plus Rust helpers to Rust plus embedded prose: the primary artifact is the Rust codebase, and the markdown that survives (briefs, references, the residual authoring surface) ships embedded in it.

One deployment, one `runtime!`-generated host binary, N+1 guests:

- **The Specify runtime binary** — a new crate in the root workspace: `omnia::runtime!({ mode: command, hosts: { WasiHttp: HttpDefault, WasiModel: Cursor, WasiOtel: OtelDefault } })`. This **is** the next `specify` executable: command mode drives one CLI invocation to completion (exit code carried through) while the HTTP trigger serves MCP routes in the background. A sibling test binary may bind `WasiModel: ModelDefault` (replay) over the same manifest for component-level tests and examples; it is not an operational mode.
- **The deployment manifest** — `omnia.toml` with one `[[guest]]` per adapter plus the workflow guest; `[[mount]]` of the operator's project directory as `"."`, writable; `[[route.http]]` prefix per adapter (`/mcp/vectis` → `vectis`, …). The workflow guest carries `link = ["augentic:specify/source", "augentic:specify/target"]`. Guests are referenced by path — the adapters repo already commits `adapter.wasm` artifacts.
- **The workflow guest** — the only guest exporting `wasi:cli/run`. It imports `source` / `target` and names the plan-bound `adapter-id` as each call's first argument, so one instance owns its own fan-out (survey over every bound source, the drained execute loop) in deterministic guest code.
- **Adapter guests** — each implements exactly one adapter axis of `specify.wit`: it exports `augentic:specify/source` **or** `/target` (never both — matching the name-uniqueness-across-axes rule), plus `wasi:http/incoming-handler` wrapping `omnia_guest::mcp::router` over its compiled-in references. Each judgment operation assembles a prompt from its embedded brief, issues `create` with an MCP grant naming its own route URL and a `grants.workspace` lend of its `"."` preopen, and deserializes the schema-validated answer into the WIT record. The workflow guest never links an adapter directly: every `survey` / `extract` / `guidance` / `build` / `merge` call crosses the host-mediated dispatch seam, with the plan-bound `adapter-id` as the routing argument.

Prose ships inside the components. The adapters repo carries roughly 292 KB of briefs and 1.5 MB of references plus 258 KB of shared rules and runtime references — trivial as an `include_str!` payload next to the existing 6.5 MB vectis component. Briefs, references, examples, and rules all stay authored and reviewed as markdown files in the repository tree; a build step embeds them, and the embedded copies are served to the spawned agent over MCP — the [`backends/examples/cursor`](https://github.com/augentic/backends/tree/main/examples/cursor) guest is the near-verbatim template for both the serving side and the grant wiring. Briefs compile in as prompt bodies; references compile in as the MCP shelf the spawned agent fetches lazily, which is the inversion's point: handles cross the model boundary, not corpora.

### Crate architecture: wasm-free cores, thin guest shims

Every guest is structured as a **wasm-free Rust library crate plus a thin `wasm32`-only shim**, following the [`wasm-replatform/train`](https://github.com/wasm-replatform/train) layout: there, all business logic lives in ordinary workspace crates that are generic over capability traits (`Config`, `HttpRequest`, `Publisher`, `StateStore`, …), and the guest entry point is a single `#![cfg(target_arch = "wasm32")]` `lib.rs` that generates the WIT exports, routes calls into the library crates, and supplies a `Provider` implementing the capability traits. The library crates compile and test natively — unit and integration tests run on the host toolchain with mock providers, no Wasmtime, no component build.

Specify adopts the same split. Each adapter root in the adapters repo doubles as its guest package: a wasm32-only `specify-<name>` shim (`src/` beside `adapter.yaml`) that owns `wit_bindgen::generate!`, the `source` / `target` export glue, and the MCP router wiring, over a wasm-free `specify-<name>-core` sub-crate at `<adapter>/crates/core/` (deterministic validation, prompt assembly, answer deserialization, the former extension-tool logic) — so the package physically contains the briefs and references it embeds. The workflow guest splits identically: the existing `specify-workflow` crate — which never linked Wasmtime — stays the wasm-free core, and a new shim exports `wasi:cli/run`. This keeps the integration-first testing posture intact: the cores are exercised through their public Rust surface natively, and only the walking-skeleton and other component-level tests need a composed component.

Omnia's guest SDK already implements this pattern for most host services: `omnia-guest::capabilities` defines one trait per capability whose methods carry WASI-backed default bodies on `wasm32` (delegating to the matching `omnia-wasi-*` binding) and bare signatures off `wasm32`, so hosts and tests supply their own. **`wasi-model` has no such capability trait yet** — `completion::create` is only reachable through the `omnia-wasi-model` bindings, which are wasm32-only. The migration therefore adds a `Model` capability to `omnia-guest::capabilities`: `create(request) -> result<reply, error>` with a WASI-backed default body on `wasm32` and a bare signature off it. Wasm-free cores take `P: Model + …` bounds and issue judgment calls through the trait; native tests bind a mock provider, giving deterministic model-leg coverage without spawning `cursor-agent` or building a component. This is the one new runtime-SDK capability the migration requires; it lands upstream in the omnia repo as a prerequisite for Step 2.

## The contract revision (`specify.wit`)

The IDL in [`wit/specify.wit`](../wit/specify.wit) was largely correct as drafted; the revision (now applied to the file) makes three changes, each forced by an implemented runtime behavior, and rewrites the doc comments — which described RFC-55-era materialized-tree semantics — to match this RFC's shared-mount model:

1. **No resources across the link seam.** Omnia's guest-to-guest dispatch carries plain values only, so `working-tree` drops its `root: descriptor` field: operations carry `base: revision` plus an optional `subpath`, and the adapter guest opens its own `"."` preopen. The descriptor survives where it belongs — the adapter lending `grants.workspace` to `create`, a host call from its own instance, which works today. The now-unused `use wasi:filesystem` imports are removed.
2. **References are the MCP export.** The typed `references` interface sketched in earlier contract drafts is superseded by the MCP server: both adapter worlds export `wasi:http/incoming-handler`, and the spawned agent fetches documents through it. A typed interface returns only if a non-spawning backend (genai's host-dispatched `resolve` via `grants.references`) is ever bound; adding it later is additive.
3. **Schema-validated answers as a convention.** `survey` returns `list<lead>`, `extract` returns `evidence`, `build` / `merge` return `report`. Every judgment leg requests `format: schema(...)` so the `wasi-model` host gate rejects malformed answers before the guest sees them, and the guest deserializes straight into the WIT record. One convention, applied uniformly across all eight adapters.

**Answer schemas come from `schemas/`.** The repo already embeds authoritative JSON Schemas in the `specify` binary, and three map directly onto the judgment answers: [`schemas/discovery/lead.schema.json`](../schemas/discovery/lead.schema.json), [`schemas/evidence.schema.json`](../schemas/evidence.schema.json), and [`schemas/target/build-report.schema.json`](../schemas/target/build-report.schema.json). The `format: schema(...)` payloads are derived from these rather than hand-written, so the host gate and the artifact validators enforce one shape. Where a schema carries more than the WIT record (evidence's `authority` and claim `kind`s, the report's `outputs` and `ui-surface`), the schema is the source of truth for the answer body and the WIT record is widened during Step 2 to carry what synthesis needs — the records as drafted are the floor, not the ceiling.

**Naming: `guidance`, not `shape`.** The WIT's `guidance` operation is canonical for the target's read-at-synthesis leg; the adapter vocabulary's `shape` term is retired when prose is updated at cutover.

Bindings are generated guest-side with `wit_bindgen::generate!` (the `omnia-guest` style) from the versioned `augentic:specify` package this repo publishes and specify-adapters consumes as a pinned dependency. No host-side bindgen is needed: Omnia's link dispatch handles the `source` / `target` interfaces structurally.

## The migration steps

### Step 1 — Runtime binary and a walking skeleton

In the existing `engine/` workspace (which moves to the root `src/` layout at the Step 5 cutover), add the `runtime!` host crate and an `omnia.toml`; add a trivial adapter guest (echo `survey`) and a trivial workflow guest that calls `survey("source:echo")` through the link import. This exercises every seam the migration depends on — manifest loading, link allow-lists, wRPC in-process dispatch, mount preopens, MCP routing, command mode with background HTTP — with zero Specify logic at risk. Wire the skeleton into CI here, first: the echo adapter needs no model at all, so the composed-component test runs without any backend.

### Step 2 — First real adapter guest (the pattern-setter)

Migrate **contracts** first (smallest prose, already a `wasm32-wasip2` crate). Build the reusable adapter-guest scaffolding here, because the other seven stamp it out:

- **Core/shim split from day one** — scaffold contracts as `specify-contracts-core` (wasm-free, natively testable, at `targets/contracts/crates/core/`) plus `specify-contracts` (the `target_arch = "wasm32"` shim at the adapter root owning bindgen and export glue), per the crate-architecture section above. The `omnia-guest` `Model` capability must already be published by this point, so the core's judgment legs are testable against a mock provider before the component ever runs.
- **Answer schemas wired to `schemas/`** — the `format: schema(...)` payloads for `lead`, `evidence`, and `report` derive from the embedded schemas (see the contract-revision section); this step establishes the derivation and reconciles the WIT records with what the schemas carry.
- **Prose registry via `build.rs`** — walk `briefs/` and `references/`, resolve the `references/spec-runtime` symlinks into `shared/references/runtime/` (symlinks do not survive compilation; the embed step inlines them), emit an embedded doc registry. This reuses the vectis `scaffold/templates/registry.rs` codegen precedent. The markdown files stay the authoring source of truth; the registry is a derived artifact regenerated on every build.
- **MCP shelf** — an `McpServer` implementation over that registry (`list_docs` / `read_doc`, `doc://` resources), served via `omnia_wasi_http::serve(mcp::router(...))` — the `examples/cursor` HTTP guest verbatim.
- **Operation template** — each `source` / `target` export: assemble prompt from embedded brief plus typed inputs, issue `create` with MCP grant + workspace lend + schema format, deserialize, then run the deterministic validate-before-visible checks **in guest Rust** after the answer lands. The old two-phase prepare/finalize handoff collapses here: what was "print envelope, exit, agent works, finalize validates" becomes one guest function whose middle is a `create` call and whose tail is the same validation code, compiled in.

This step also answers the migration's riskiest question: **sessions do not exist.** The cursor backend spawns a fresh, context-free agent per `create` with a two-attempt repair loop. Operations that today lean on editor-chat continuity must decompose into single-shot `create` calls with all state carried in the workspace files and the prompt. Prove the decomposition on contracts' build sub-flows before scaling to vectis.

### Step 3 — Roll out the remaining adapters

- **Agent-only sources** (intent, documentation, typescript, screenshots, captures): thin crates — no deterministic core, just brief-prompted `create` calls returning `list<lead>` / `evidence` through the schema gate.
- **Vectis and contracts extension tools**: the existing extension crates stop being separately-dispatched WASI tools and become plain library code inside the adapter guest — `validate` / `materialize` / `prepare` are ordinary Rust called before and after the model leg. `specify extension run` and the engine's registry-hosted Wasmtime runner become redundant.
- **Omnia target**: the largest reference shelf (roughly 700 KB across 65 files) — the strongest case for MCP-served references over prompt-pasting.
- **Workspace mechanics**: the specify-adapters Cargo workspace grows from 3 members to one crate per adapter; each adapter directory keeps its prose as the authoring source of truth, with the component as the build artifact. The `adapter.yaml` brief-path and `execution: agent` machinery becomes vestigial once nothing reads manifests for agent handoffs.

### Step 4 — The workflow guest

Port the plan/slice loop from the engine's `workflow` crate and CLI dispatch into the guest. This step completes the workflow's move from prose to Rust: everything the phase skills currently narrate as orchestration — which CLI verb to run next, when to fan out, when a transition is legal — becomes guest control flow, and nothing about workflow sequencing remains agent-interpreted.

- **Deterministic sequencing compiles in**: `plan next`, transition legality, artifact-completion checks, journal writes, survey fan-out, the drained execute loop. `specify-workflow` never linked Wasmtime and stays the wasm-free core; the guest shim is a thin `wasi:cli/run` exporter over it — swap native paths for the `"."` preopen and keep the validated formats identical.
- **Judgment stays model-driven**: lead reconciliation, synthesis, and refine-phase authoring become `create` calls (through the `Model` capability, so the core stays natively testable) with the relevant **skill** prose compiled in as system/prompt text — this is where `plugins/spec/**` markdown moves from "agent reads it" to "guest sends it".
- **Lifecycle authority** stays where it effectively is today — the same Rust validators, now inside the guest rather than behind a CLI subprocess. `.specify/` files remain the durable state, which is also what makes in-place coexistence safe.
- **Operator surface**: `specify plan …` / `specify slice …` argv maps onto the guest's `wasi:cli/run`; command mode's exit status carries through. Every `/spec:*` skill becomes an **ultrathin wrapper**: elicit any missing arguments, invoke the corresponding `specify` command, relay its output. No skill retains orchestration prose, phase sequencing, artifact synthesis instructions, or validation logic — a skill that cannot be reduced to "invoke and relay" indicates workflow logic that belongs in the guest and must be ported before the skill is thinned. Skills whose entire body was orchestration (e.g. the execute loop) retire outright once the guest owns their behavior.

### Step 5 — The cutover

The cutover is **all at once**: there is no per-operation halfway state where some phases run native and others run through the runtime. Steps 1–4 build and validate the guests alongside the native path — which remains the sole operational surface throughout — and once every guest is proven, one release (the migration PR itself — see [Delivery](#delivery-one-pr-per-repo)) swaps the binary and deletes the old stack in the same change: the handoff-envelope machinery, `extension run` and the engine registry's Wasmtime host, and the native orchestration commands — leaving the `runtime!` binary as `specify`. The same cut restructures the repository into the target shape: the Rust code in `engine/` moves to a root `src/` directory, the workspace root becomes the repository root, and the surviving prose is embedded — the repo lands as Rust plus embedded prose, not prose plus Rust helpers. Prose (skill thinning, vocabulary renames like `shape` → `guidance`) is updated in the same cut, per the no-compatibility-alias rule for major changes.

**The lint framework shrinks with the prose it polices.** Most `CORE-*` checks exist because prose currently carries load-bearing workflow structure that must be kept consistent with the binary by hand: skill bodies citing CLI verbs (`cli-contract`), workflow-term cross-references, set-coverage and field-grammar over adapter manifests, the skill-body caps and envelope checks. Once sequencing is guest Rust, skills are invoke-and-relay wrappers, and the `adapter.yaml` handoff machinery is vestigial, those consistency classes are enforced by the type system and the WIT contract — a renamed verb or a dropped operation is a compile error, not a lint finding — and the checks are deleted alongside the prose they policed. The surviving surface is small: authoring house style for the markdown that remains (briefs as prompt bodies, references and examples as the MCP shelf), and doc-link resolution, which moves into the `build.rs` embed step where a dangling reference fails the build rather than the lint. The residue stays **native Rust** — host-side code in the root workspace run by `make lint`, never a guest. `specify lint project` — engineering standards over consumer-project code — is untouched by this; it never policed this repo's prose.

## Constraints designed around

Implemented-runtime behaviors the design accommodates rather than changes:

- **Single CLI exporter.** `[[route.cli]]` is not parsed; with multiple `wasi:cli/run` exporters startup routing fails. Convention: only the workflow guest exports the CLI world; adapters are reached exclusively through link dispatch and HTTP.
- **Compile-time backend binding.** One deployment binds one `WasiModelCtx`. Cursor for the real binary, replay for component-level tests and examples — two `runtime!` invocations over the same manifest. A per-call router is out of scope.
- **Guests ship by path.** OCI guest sources are parsed but rejected at load; the manifest references committed `adapter.wasm` files on disk, which suits an in-place migration.
- **MCP URLs are absolute.** The grant carries a full endpoint URL; guests read the host/port via `wasi:config` or environment rather than hardcoding, since `HTTP_ADDR` is deployment-configurable.
- **Session-less model calls.** Fresh spawn per `create`, two-attempt repair, no transcript reuse. Long adaptive operations decompose into single-shot calls with state in the working tree (Step 2 proves this).
- **Shared mounts, not materialized trees.** All guests see the same `[[mount]]` preopens, so `build` / `merge` run against the operator's live project tree exactly as the native CLI does today. Distributed, content-addressed working trees ([RFC-55](future/rfc-55-working-tree.md)) are deferred until a multi-node deployment exists; the `revision` / `changeset` types stay in the contract as their forward hook.
- **`verify` is stubbed.** The grant is accepted but unimplemented; generated-code verification keeps running through the adapters' existing native check flows until [RFC-60](future/rfc-60-verify-profiles.md) is revisited.

## Delivery: one PR per repo

The migration is completed and merged as **a single PR in each affected repo** — the steps are branch-internal milestones, never merged increments. `main` never carries both stacks: the native path remains the sole operational surface until the specify PR merges, and merging it **is** the Step 5 cutover.

- **Branch discipline.** Each step lands as one commit (or one contiguous commit range) on the migration branch, green under `make lint` and `cargo make ci` at every step boundary, so the PR is reviewable step-by-step. Intermediate commits carry both stacks; the PR head is the post-cutover state with the old stack deleted.
- **Cross-repo landing order.** A single PR cannot span repos, so the coordination is ordered pins (per the roadmap's [cross-repo coordination](roadmap.md#cross-repo-coordination)): first the `Model` capability lands in `augentic/omnia` (operator-handled, prerequisite for Step 2); then the `augentic:specify` WIT pin is made consumable (`wkg` publishing is operator-handled during the initial build); then the specify-adapters PR ships the adapter guest crates and their committed `adapter.wasm` artifacts against that pin; finally the specify PR — runtime binary, workflow guest, deletions, skill thinning — references those committed artifacts from its `omnia.toml` and cuts over on merge.
- **The Step 2 → Step 4 gate is reviewable.** With no merged increments to earn trust on, the decomposition proof runs on the branch against the [`evals/`](../evals/README.md) fixtures and scenario packs; "contracts has demonstrated the answer" means passing eval runs a PR reviewer can inspect, not an assertion.

Shared state is what makes the branch-side validation safe: `.specify/` artifacts, `plan.yaml`, and the journal are the only state both stacks touch, and both read and write them through the same validated formats — so guests can be exercised against real project trees on the branch without the two stacks colliding.

## Acceptance criteria

1. The `runtime!` Specify binary hosts the workflow guest plus all eight adapter guests from one `omnia.toml`; command mode drives the operator CLI and background HTTP serves each adapter's MCP shelf.
2. `specify.wit` carries no resource types across guest-to-guest calls, and every adapter world's reference surface is the MCP export; guest bindings are generated from the published package in both repos.
3. Every adapter judgment operation runs as a schema-gated `create` against the cursor backend, with its brief compiled in, its references fetched over MCP by the spawned agent, and its answer schema derived from the embedded `schemas/` documents.
4. The vectis and contracts extension tools run as in-guest library code; `specify extension run` is deleted.
5. The workflow guest owns plan/slice sequencing and fan-out; lifecycle validation runs in-guest over `.specify/` state; the bespoke handoff envelopes are deleted.
6. Every `/spec:*` skill is an ultrathin invoke-and-relay wrapper around a `specify` command (or retired); no skill body carries orchestration, synthesis, or validation prose.
7. Every guest is a wasm-free core crate plus a `wasm32`-only shim; the cores' tests (including model-leg tests through the `Model` capability trait with a mock provider) run on the native toolchain without a component build.
8. The framework lint surface is reduced to authoring house style plus embed-time link resolution, running as native Rust; every `CORE-*` check whose consistency burden moved into the type system or the WIT contract is deleted with the prose it policed.
9. The repository lands in the target shape: the Rust code formerly under `engine/` lives in a root `src/` directory with the workspace at the repository root, and the surviving prose ships embedded in the Rust artifacts.
10. `make lint` and `cargo make ci` are green at every step-boundary commit on the migration branch; the PR head is the post-cutover state, and the native path remains the sole operational surface on `main` until that PR merges.

## Risks and invariants

- **Decomposition risk is front-loaded.** The plan's riskiest unknown — whether long, adaptive operations survive decomposition into session-less `create` calls — is answered in Step 2 on the smallest adapter, before the workflow port begins. Do not start Step 4 until contracts (and ideally one vectis build leg) has demonstrated the answer.
- **Hardening is deliberately deferred.** The cursor backend runs `cursor-agent --force --trust` against the operator's live tree and merges MCP grants into its `.cursor/mcp.json`. Sandboxing, permission narrowing, and prompt-injection defenses are out of scope until the migration is proven end-to-end; hardening the framework is the phase after this RFC, not a gate on it.
- **Prose stays authored as files.** Briefs, references, examples, and rules remain markdown in the adapter trees; embedding is a build step and the MCP shelf serves the embedded copies. Authoring workflow and review do not change; `make lint` coverage holds throughout the migration and then shrinks at Step 5 to the residue the type system cannot carry — house style and embed-time link resolution.
- **Wasm specifics stay in the shims.** Core crates never gate on `target_arch = "wasm32"`, never call `omnia-wasi-*` bindings directly, and reach every host service — the model included — through capability traits. A core that needs a `cfg(target_arch)` is a design error; the code moves to the shim or behind a trait.
- **Don't ossify the fluid.** Deterministic sequencing graduates into guest code; judgment stays behind `create`. A phase that needs the model to sequence stays model-driven.
- **The contract stays adapter- and model-agnostic.** No adapter name, taxonomy, or model id enters `augentic:specify`; the model id lives in the backend binding, never in a guest.
- **Omnia stays domain-free.** Everything Specify-specific lives in the guests, the deployment manifest, and the Specify runtime binary's backend selection — never in the Omnia runtime core.
