# Migrating from Specify 1.x to 2.0

Specify 2.0 is a hard cut from 1.x. There are no compatibility aliases for
old manifests, verbs, brief paths, or `/change:*`. To upgrade a project,
run `scripts/migrate-to-2.0.sh` once. The script performs every mechanical
rename the release requires; you finish by re-syncing your plugin
marketplace and (when applicable) stamping any in-flight plan back to
`reviewed`.

## Before you run

1. Commit or stash any local changes. The script writes in place; you
   want a clean diff to review.
2. Confirm `.specify/project.yaml` and `.specify/plan.yaml` parse as
   YAML.
3. Make sure Deno is installed and on `PATH` (or under
   `$HOME/.deno/bin/`). The migration script invokes Deno once; it does
   not stay resident afterwards.
4. Take a snapshot if you're cautious: `cp -R .specify .specify.bak`.

## Running the script

From the project root:

```bash
./scripts/migrate-to-2.0.sh --dry-run    # preview every change
./scripts/migrate-to-2.0.sh              # apply
```

Or pass an explicit project root:

```bash
./scripts/migrate-to-2.0.sh --dry-run /path/to/project
```

The script is idempotent. A second run on an already-migrated tree exits
0 with `info  already on specify 2.0.0; nothing to do` (still warns about
retired skills and `composition.yaml` if it sees them).

## What it changes

| Surface | 1.x | 2.0 |
| --- | --- | --- |
| `adapters/` at the project root | dir of operator-authored target adapters | renamed to `targets/` |
| `.specify/project.yaml` | `adapter:`, `specify_version:`, `hub:` | `target:`, `specify-version:` (kebab-case, bumped to `2.0.0`), `workspace:` |
| `.specify/registry.yaml` | per-project `adapter:`, `proposed-adapter:` | `target:`, `proposed-target:` |
| `.specify/sources.yaml` | per-source `value:` | per-source `path:` |
| `.specify/plan.yaml` slices | `slices[].adapter:`, bare-string `sources: [key, ...]`, optional standalone `slices[].candidate:` | `slices[].target:`, structured `sources: [{ key, candidate }]` with any standalone `candidate:` lifted into each binding |
| `.specify/plan.yaml` lifecycle | `pending | reviewed | in-progress | drained` | `pending | reviewed` (the script collapses `in-progress` and `drained` to `reviewed`) |
| `.specify/plan.yaml` per-entry status | adds `blocked`, `failed`, `skipped` | the script rewrites those to `pending` so the operator restarts the slice |
| `.specify/archive/plans/<id>/plan.yaml` | as above | same transforms; per-entry `status: done` is preserved (archives are historical record) |
| `.specify/.cache/adapters/<name>/` | per-target cache scope | renamed to `.specify/.cache/targets/<name>/` |
| `.specify/specs/<slice>/layout.yaml` | hand-authored baseline artifact | renamed to `.layout.yaml.deprecated`; re-emit equivalent data via `screenshots.extract` Evidence |
| `.specify/specs/<slice>/composition.yaml` | hand-authored baseline artifact | warning only; the file becomes a build output regenerated by `targets/vectis/build` on the first 2.0 `/spec:execute` |
| Vectis schema `$id` URLs in any `composition.yaml` / `tokens.yaml` / `assets.yaml` | `https://github.com/augentic/specify/{adapters,schemas}/vectis/<schema>.schema.json` | rewritten to `https://github.com/augentic/specify/targets/vectis/schemas/<schema>.schema.json` |

## What it does NOT change

- Your code (`src/`, `crates/`, `apps/`, etc.).
- Spec content in `.specify/specs/**/spec.md`, `design.md`, `tasks.md`.
- Archived `change.md` files.
- Anything outside `.specify/`, `adapters/`, and `plugins/vectis/skills/image-layout-inferer/`.

## Vectis schema relocation

The Vectis shared assets (`composition.schema.json`, `tokens.schema.json`, `assets.schema.json`, codex rules, and the operator-facing `tokens.yaml` example) moved from `adapters/vectis/` to `targets/vectis/{schemas,codex,examples}/` in 2.0. The published schema `$id` URLs broke deliberately: the new canonical form is

```text
https://github.com/augentic/specify/targets/vectis/schemas/<name>.schema.json
```

The `$id` URLs are opaque identifiers, not fetch targets, so this only affects tooling that compares URLs for cache invalidation or vendor-prefixes the URL when rendering schema docs. The migration script auto-rewrites any embedded `$id` reference inside `.specify/specs/**/composition.yaml`, `tokens.yaml`, and `assets.yaml` (legacy `adapters/vectis/...` and `schemas/vectis/...` URL forms both rewrite to the new `targets/vectis/schemas/...` form). External tooling that pinned the old URLs needs a one-line update on its side.

## Manual steps after migration

1. **Re-sync your plugin marketplace.** Cursor users: re-run the plugin
   marketplace sync (the `image-layout-inferer` body has moved to
   `sources/screenshots/`). `/spec:*` skill bodies were rewritten across
   the wave; you want the new copies.
2. **Decide on existing `composition.yaml` files.** The migration warns
   but does not delete them. After your first 2.0 `/spec:execute`
   regenerates them via `targets/vectis/build`, diff and remove the old
   copies.
3. **Stamp plans that were in flight.** If the script collapsed your
   plan from `in-progress` (or `drained`) to `reviewed`, you may resume
   `/spec:execute` directly. If you'd rather amend the plan first, run
   `specify plan transition <name> pending` and re-stamp `reviewed`
   manually. Plans previously parked at `pending` stay at `pending`.
4. **Review the diff.** The script emits one line per file changed.
   Spot-check `.specify/plan.yaml`'s slice bindings to confirm any
   bare-string `sources:` lifted into the right `{ key, candidate }`
   shape.

## Troubleshooting

- **`not a Specify project: missing .specify/project.yaml`** — you ran
  the script outside the project root. Pass the path explicitly:
  `./scripts/migrate-to-2.0.sh /path/to/project`.
- **`plan.yaml slice "<name>" has bare-string sources but no candidate
  to lift`** — the slice has neither a `name:` nor a standalone
  `candidate:` field; we can't synthesise the binding `candidate:`.
  Hand-add either a `name:` (recommended) or a `candidate:` line to the
  slice and re-run.
- **`both adapters/ and targets/ exist at project root; leaving
  adapters/ in place for manual review`** — you already had a 2.0-shape
  `targets/` directory. Merge by hand, delete the empty side, and re-run.
- **`both .specify/.cache/adapters/ and .cache/targets/ exist`** — same
  resolution: merge by hand. Cache contents are regenerable, so
  `rm -rf .specify/.cache/adapters` is often the right call.
- **`Deno not found on PATH.`** — install Deno
  (<https://docs.deno.com/runtime/getting_started/installation/>) or
  pass `DENO=/path/to/deno`. The dependency is one-shot.
