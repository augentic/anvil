# Architecture

Workspace shape, crate dependency direction, the WASI carve-out, and the `.emery/` layout boundary. Read this before adding a new crate or shifting where state lives.

## Workspace layout

Deployment crate (`name = "emery"`) at the repo root. The native arm of [`src/lib.rs`](../../src/lib.rs) is the `deployment!` macro: one `omnia::runtime!` command-mode invocation over the cursor-bound backends, with the plugin `locations:` list as its only parameter, expanded by the shipped binary ([`src/main.rs`](../../src/main.rs)) with the path root and the `omnia.host` registry, and by the journey host ([`examples/runtime.rs`](../../examples/runtime.rs)) path-only. The engine guest is embedded as static component bytes (`include_bytes!` over `$OUT_DIR/emery.cwasm`, produced by the root `build.rs` — a child wasm32 build into `target/wasm32-engine`, one directory shared by every outer feature set, profile, and lock revision rather than nested under the per-hash `OUT_DIR`, then in release builds an ahead-of-time wasmtime serialize so startup deserializes instead of JIT-compiling the engine; debug builds embed the raw component and JIT at startup; there is no placeholder fallback). Deployment policy is static and CWD-rooted: the invocation directory mounts read-only as the guest's `.` — nothing writes the working tree, the C3 least-authority posture (no ancestor walk — a verb run below the project root fails typed), the storage hosts bind the revision store to the durable omnia-filesystem store (compiled-in root `.omnia/storage`), and the `plugins:` block declares the source seam (`emery:adapter/source@0.1.0`) plus the caller's acquisition policy as a declarative `locations:` list (the `.` path root — preopen-aligned reads, fresh on every load, never cached — then, in the shipped binary, the `omnia.host` registry endpoint, likewise read fresh: the runtime declares no project cache). The shipped runtime embeds the engine only: a local `.wasm` adapter loads at run time through the `omnia:plugins/loader` capability, an exact package reference fetches from its registry, and bare names still dispatch only statically declared guests. Every invocation — help, version, and grammar rejections included — runs in the emery guest (the wasm32 arm of [`src/lib.rs`](../../src/lib.rs)) through the shared command grammar (`emery_cli`).

The authoritative leaf → root crate graph (with per-crate roles) lives in [AGENTS.md](../../AGENTS.md). Headline shape: `prose` (the embedded-corpus registry) and `source` (the `emery:adapter/source` contract, both sides) are the leaves; `adapter` is the guest-only SDK over them; `engine` owns the transport-neutral domain operations (`specify`, `show`, adapter resolution) and returns `omnia_guest::Error` from them; `cli` (`emery-cli`) is the command grammar over the engine — clap grammar, source carriers, per-body text render fns, hint table — driving omnia's command façade (`omnia_guest::api::command`) for dispatch, projection, and the exit map; the root package's `src/lib.rs` owns native deployment policy (the `deployment!` macro, its native arm) and is the one provider on wasm32 (the component contract is the only production boundary). The journey's mock adapter is the root-package `adapter` example (`examples/adapter/lib.rs` plus its embedded `prose/`), the same `SourceAdapter` + `source!` anatomy as a first-party adapter. The `runtime` example stays on the root package because it embeds `$OUT_DIR/emery.cwasm`.

There is no lint engine or `Check` substrate. Repo consistency is the mdBook links gate (`make links`).

Evidence claim types live in `source` (the WIT-shaped DTOs, re-exported by the adapter SDK); the fail-closed `spec.md` parser lives in `engine`. Neither depends on anything named lint.

### Engineering standards live in the adapters

There is no standards crate: engineering-standards rules (`UNI-*` and per-adapter overlays) are authored in `augentic/emery-adapters` and ship embedded in each target adapter's component, applied by its build review prompts. The "no lifecycle authority in review" rule is structural — no engine crate parses or resolves rules, so standards prose cannot reach slice or plan transitions.

Every crate uses the shared `[workspace.package]` (`edition = "2024"`, `rust-version = "1.98"`, MIT/Apache-2.0) and the shared `[workspace.lints]` block in the root `Cargo.toml` (clippy `all`/`cargo`/`nursery`/`pedantic` warned, plus a hand-picked `restriction` subset and a tightened rust lint set — `missing_debug_implementations`, `single_use_lifetimes`, `redundant_lifetimes`).

**Hard dependency rule:** `prose` and `source` are the leaves and depend on no other workspace crate; `adapter` depends on both and nothing else; no production crate depends on `adapter` (the root package links it as a dev-dependency for `examples/adapter` only). The engine reaches the contract and the corpus registry through the leaves, never through the SDK — before this split the engine guest linked the whole judgment SDK to reach the wire types. Adding a workspace dep to a leaf, or an `adapter` dep to `engine` or the root's production arms, re-introduces that coupling; do not. The command boundary is one-directional too: `cli → engine`, never the reverse, and `engine` carries no `clap`, `clap_complete`, or `toml` dependency and no terminal vocabulary (flag names, verbs, stdout, exit codes) in its types, docs, or error descriptions — omnia's `api::http` overlay must type-check over `emery_engine::specify::Specify` / `emery_engine::show::Show` with no engine edits, and `cargo tree -p emery-engine -e normal --depth 1` stays free of the façade crates. Only the root's wasm32 arm and the root suites depend on `cli`.

**New workspace crates** are an exception, not the default. Capability doubles are not a local crate: the native suites take them from omnia's `omnia-test` (`guest::{Scripted, ScriptedLoader, Memory, Namespaced}`, `delegate!`). No test-only package builds a component here; the wasm boundary is instantiated by `emery-adapters`' conformance rung and guarded in this repository by `make wasm`.

The `adapter` example (`examples/adapter/`) is the one mock source adapter: a `emery_adapter::SourceAdapter` implementor whose extract calls the host `Model` over its fixture tree (`examples/docs/`). The `runtime` example hosts it with the Cursor backend and a path-only plugin `locations:` list. It carries no production lifecycle authority and never enters the shipped guest. Do not add another mock adapter — extend this example.

## Deployment: the Wasm guest

The guest's provider is a bare unit at the composition root (`src/lib.rs`) carrying the engine's capabilities: the model (`omnia_guest::Model`, WASI-backed defaults), the `Source` capability (`emery_source::Source`), the storage pair (`omnia_guest::StateStore` / `BlobStore`, since design/portable-storage.md steps 1–2), whose wasm32 default bodies ride the `wasi:keyvalue` / `wasi:blobstore` imports, and the plugin loader (`omnia_guest::Plugins`, whose wasm32 default rides the `omnia:plugins/loader` import); the runtime binds those hosts to the durable `omnia-filesystem` store (compiled-in root `.omnia/storage`; the `deployment!` macro in the native arm of `src/lib.rs`), so the backing is deployment policy, never engine code — alternative bindings, project-id-keyed multi-project hosts included, are documented in [deployment profiles](../reference/deployment-profiles.md). Everything else is structural: paths are fixed constants relative to named preopens (the `.` project mount; `emery_engine::preopen_path` normalizes operator paths inside it), and adapter dispatch — `extract` and `metadata` — rides the `emery:adapter/source` WIT imports directly from the engine's cfg-gated dispatch functions (typed refusals on native, where no WIT import exists). The native provider was deleted at the Phase 3 spine cut; the product arc's native coverage is the root scenario rung (`tests/specify.rs`), while pure kernels test over scripted capabilities.

The root `emery` package carries the Omnia deployment unit under `src/`: the guest cdylib (the wasm32 arm of `src/lib.rs`, the `wasi:cli/run` exporter plus the bare model provider — there is no HTTP export; C3 is satisfied by binding no listener at all) and the shipped runtime (`src/main.rs`, expanding the `deployment!` macro from the native arm of `src/lib.rs` — one `omnia::runtime!` invocation embedding the engine bytes). Operations live in `engine` as `Handler<P, I>` fns (`specify`, `show`) over transport-neutral serde inputs (`Specify`, `Show`; path plumbing in `emery_engine::preopen_path`). `emery_cli` owns the clap grammar, the source carriers, and the per-body render fns; `emery_cli::run` binds the caller's provider into a `Client` for one argv and drives omnia's `Command` projector over it. The WASI shim (`omnia_guest::command!(dispatch)`) constructs the provider, runs that grammar, and hands the `Response` to `omnia_guest::api::command::execute_wasi`. The routing design is documented in [handler-shape.md](handler-shape.md).

## Domain modules of note

- **`crates/engine/src/plugin.rs`** — source-adapter loading over the typed `AdapterRef`: selector parsing, the per-run `Loader` memo issuing the `omnia:plugins/loader` load request for local components and registry packages (over the provider's `Plugins` capability, threading the source's digest pin and registry override and returning the routed dispatch id), and the adapter `emery-version` gate, dispatched directly over the provider's `Source` capability (the WIT `metadata` import on wasm32, a scripted mock natively).
- **Asking the model** — the engine owns no completion loop. Each of the three judgments is an `omnia_guest::model::Question<T>` (`grouping`, `spec-draft`, `design-draft`): `T`'s derived draft-2020-12 schema rides the request as the steering hint, tightened per run by a `hints` edit beside the answer type (row subjects and exact counts on `SpecAnswer`, the plan's section kinds and the run's `type` keys on `DesignAnswer`, index bounds on `Grouping`), and acceptance is the request's `check` — the engine's semantic `check` fn, run over every candidate the backend proposes. A miss goes back as the correction (`## Previous answer (rejected)` / `## Findings`), written by omnia, and the backend asks again within its own round budget; the engine never sees the reply text. `From<model::Error>` does the exit map: a serde mismatch or spent rounds is `bad_request` carrying the last correction, a model failure `bad_gateway`. Hints steer only; every rule stays in `check`.
- **`crates/engine/src/specify/provenance.rs`** — requirement identity and status. Every `requirement` claim is indexed in source order; a run over two or more sources asks the model for one `Grouping` — a partition into requirements, each partitioned into agreeing classes — with authority withheld, validated as a partition over the byte-equal-id floor (a floor pair split is a finding); a run over one source takes the floor alone with no model turn. `derive` then sorts every class by authority and source order, sorts classes by their top contributor, and reads off each requirement's `Provenance` — the row `spec.md` renders: the subject (the top contributor's id), `Status` (one class agreed; a unique top authority divergence; tied top authorities conflict; agreed-but-uncovered unknown), whether any `criterion` id equals or dot-extends a contributor id, and the classes themselves for the loser notes.
- **`crates/engine/src/specify/answer.rs`** — the two typed content answers, `SpecAnswer` (preamble, one `{ subject, body, scenarios }` per row) and `DesignAnswer` (preamble, one `{ kind, blocks }` per section with `{ text }` or `{ type }` blocks), their per-run schema `hints`, and the semantic checks the schema cannot express: the subject set equals the row set exactly once, a scenario per requirement, no body on a conflict row and at least one otherwise, the section set equals the plan's required set plus informed permitted ones, every `type` claim referenced exactly once and only under `domain-model`, every `(from <key>)` bound, and no paragraph line opening with a marker the renderer owns.
- **`crates/engine/src/specify/render.rs`** — the canonical projection: rows + `SpecAnswer` → `spec.md` and the extracted evidence + `DesignAnswer` → `design.md`. The renderer writes every heading, `ID:` / `Sources:` / `Status:` line, heading tag, `Note:` line (one per losing class, the operator hand-off line for a conflict, the acceptance gap), scenario bullet, and fenced `type` signature; the model's paragraphs are placed, never parsed. The layout is frozen byte-for-byte by the root scenario fixtures, and a render → read round trip beside the renderer holds the two grammars together.
- **`crates/engine/src/artifact.rs`** — the canonical reader over the stored documents and the vocabulary the renderer and reader share (`Document` — the two file names, `HEADING`, `SCENARIO`, `ReqId`, `Status`, `SectionKind`). Used by the re-mine diff alone: a stored document that does not fit its grammar was not rendered by this engine, so the reader returns `server_error` and `Diff::between` falls back to the byte-level artifact list.
  - **`artifact/spec.rs`** — reads `### Requirement:` blocks (subject, `Sources`, `Status`, body) keyed by subject.
  - **`artifact/design.rs`** — reads `## ` sections of the closed vocabulary (`Overview`, `Domain model`, `APIs and integrations`, `Technical logic`, `UI / layout`, `Observability`) in fixed order, keyed by kind; also home to the `(from <key>)` citation scanner the draft check reuses.

The lenient v1 module trees (provenance, the task/decision/leads validators) were deleted at the Phase 3 spine cut and are documented at tag `v1`.

## Adapter component resolution

Resolution dispatches identities by routed id (the WIT `metadata` export). A local component selector or an exact package reference loads through the deployment's `omnia:plugins/loader` capability once per adapter identity on every `specify` that names it: the host's acquirer reads a component file fresh (nothing is mirrored, so a deleted file refuses typed on the next run) or fetches a package from the source's `registry` override or the compiled-in default endpoint, verifies the source's optional sha256 pin before validation, validates the component against the declared source seam, and registers it — a component under its `source:<name>` routed id, a package under the package reference itself. Bare selectors still dispatch only guests declared in the runtime invocation; anything else fails at dispatch. There is no sibling-checkout or build-tree probe. Storage locations are fixed key and container-name formulas — the same names resolve against whatever backing the deployment binds. A binding names the axis; a component bound on the wrong axis fails at dispatch — no deployed guest exports the requested `<axis>:<name>` id.

## WASI carve-outs

The two adapter validators — `contract` and `vectis` — are in-guest adapter library code compiled into each adapter's published component in `augentic/emery-adapters`. The carve-out discipline (leaner lint posture and minimal `[workspace.dependencies]`) lives in that repo's workspace. Crux shell presence and launcher-icon heuristics live in the vectis adapter's in-guest core: the host performs no plan-time shell detection, so this repo carries no shell-detect crate.

**Host runner invariant.** The host CLI dispatches no adapter-owned tool: adapter validation, scaffold, and rendering logic lives entirely in the adapters repo as in-guest library code. There is no declared-tool surface. No `emery-*` workspace crate may import adapter-specific validation, scaffold, or rendering logic.

## Layout boundary

`.emery/` is framework-managed state every CLI verb writes through, and the engine's private `store::Store` is its one owner: the revision store (revision documents plus the current revision id) over the deployment's storage capabilities. Do not hard-code `.emery/` paths elsewhere; a new `.emery/` location lands on that owner.

## Toolchain

Rust stable per `rust-toolchain.toml` (channel `stable`, components `clippy`, `rust-src`, `rustfmt`). WASM targets pre-installed via `targets = ["aarch64-apple-darwin", "wasm32-wasip2", "x86_64-apple-darwin"]`.

`rustfmt.toml` uses unstable nightly features (`unstable_features = true`, `imports_granularity = "Module"`, `group_imports = "StdExternalCrate"`). Format with nightly:

```bash
cargo +nightly fmt --all
```

`make fmt` does this for you.

## Supply chain

`cargo-vet` and `cargo-deny` gate `make ci`; `cargo-audit`, `cargo-outdated`, and `cargo-udeps` are advisory tasks run on demand (`make audit` / `outdated` / `deps`). The vet task is check-only (`cargo vet --locked`) — regeneration is deliberately not part of the gate, since regenerating exemptions before checking would auto-exempt anything unaudited. When a new dependency lands:

1. Add it to `[workspace.dependencies]` in the root `Cargo.toml` with a major-version pin (e.g. `serde = { version = "1", features = ["derive"] }`). Per-crate `Cargo.toml` references it as `serde.workspace = true`.
2. Run `cargo vet regenerate imports`, `cargo vet regenerate exemptions`, and `cargo vet regenerate unpublished`; review the `supply-chain/` diff, then commit it.
3. Check `deny.toml` allows the dependency's licence. The current allowlist is in `deny.toml`; add a new SPDX id only after confirming compatibility with MIT-OR-Apache-2.0.

`clippy::multiple_crate_versions` is silenced workspace-wide (`Cargo.toml`'s `[workspace.lints.clippy]`); duplicate transitive versions are audited by hand via `cargo tree --duplicates` on each `cargo update`, not gated through a ratchet.

## Skill / CLI responsibility split

Every deterministic operation lives in this CLI: kebab-case validation, adapter resolution and loading, and schema validation. The surviving `/emery:specify` skill shells out for all of those.

The corollary: when a skill currently does something deterministic in prose (parsing YAML, validating shape, transitioning state), the right fix is to add a CLI verb here and have the skill call it. The wrong fix is to make the skill smarter.

[`AGENTS.md`](../../AGENTS.md) is the source of truth for vocabulary and the crate map.
