# Anatomy of a Schema

A schema configures how Specify generates artifacts and builds code for a particular technology stack. When a user runs `/spec:init`, the schema URL they provide determines which brief pipelines run during define, build, and merge.

## Directory layout

Each schema lives under `schemas/<name>/`:

```text
schemas/
├── omnia/
│   ├── schema.yaml             # Pipeline declarations + domain context
│   └── briefs/
│       ├── proposal.md
│       ├── specs.md
│       ├── contracts.md
│       ├── design.md
│       ├── tasks.md
│       ├── build.md
│       └── merge.md
├── vectis/
│   ├── schema.yaml
│   └── briefs/
│       ├── proposal.md
│       ├── specs.md
│       ├── contracts.md
│       ├── composition.md      # Vectis-specific stage
│       ├── design.md
│       ├── tasks.md
│       ├── build.md
│       └── merge.md
└── contracts/
    ├── schema.yaml
    └── briefs/...
```

## `schema.yaml`

The `schema.yaml` file is the schema's entry point. It declares the pipeline phases and provides default domain context. It is validated against `.cursor/schemas/specify-schema.schema.json` in this repository and against `specify-cli/schemas/schema.schema.json` in the CLI.

Here is the Omnia schema as a concrete example:

```yaml
# yaml-language-server: $schema=../../.cursor/schemas/specify-schema.schema.json
name: omnia
version: 1
description: Omnia Rust WASM workflow
domain: |
  Tech stack: Rust, WASM (wasm32-wasip2), Omnia SDK
  Architecture: Handler<P> pattern with provider trait bounds
  Testing: Rust integration tests, cargo test

pipeline:
  plan:
    - id: discovery
      brief: briefs/plan/discovery.md
    - id: propose
      brief: briefs/plan/propose.md
  define:
    - id: proposal
      brief: briefs/proposal.md
    - id: specs
      brief: briefs/specs.md
    - id: contracts
      brief: briefs/contracts.md
    - id: design
      brief: briefs/design.md
    - id: tasks
      brief: briefs/tasks.md
  build:
    - id: build
      brief: briefs/build.md
  merge:
    - id: merge
      brief: briefs/merge.md
```

### Top-level fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Schema identifier (e.g. `omnia`, `vectis`) |
| `version` | integer | yes | Schema version number (minimum 1) |
| `description` | string | yes | Human-readable description of the schema |
| `extends` | string | no | URL of a parent schema for composition (child inherits pipeline entries and brief files not explicitly overridden) |
| `domain` | string | no | Default project context describing the tech stack, architecture, and testing approach |
| `pipeline` | object | yes | Pipeline phases with ordered brief references |

### Pipeline structure

The `pipeline` object has three required phases -- `define`, `build`, and `merge` -- plus an optional `plan` phase for Layer 3 initiative authoring:

| Phase | When it runs | Minimum entries |
|-------|-------------|-----------------|
| `plan` | `/spec:plan` (Layer 3 authoring) | 2 (discovery + propose) |
| `define` | `/spec:define` (artifact generation) | 1 |
| `build` | `/spec:build` (implementation) | 1 |
| `merge` | `/spec:merge` (baseline merge) | 1 |

Each phase contains an ordered array of **pipeline entries**:

```yaml
- id: specs
  brief: briefs/specs.md
```

| Field | Description |
|-------|-------------|
| `id` | Brief identifier (must be unique across all phases within the schema) |
| `brief` | Relative path from the schema directory to the brief markdown file |

## Brief files

Each brief is a markdown file with YAML frontmatter. The frontmatter declares metadata; the body contains the generation or implementation instructions that the agent follows.

### Brief frontmatter

```yaml
---
id: specs
description: Generate behavioral specifications from the proposal
generates: "specs/**/*.md"
needs: [proposal]
---
```

| Field | Required | Description |
|-------|----------|-------------|
| `id` | yes | Must match the `id` in the corresponding pipeline entry |
| `description` | yes | What this brief produces or does |
| `generates` | no | Output filename or glob pattern (e.g. `proposal.md`, `specs/**/*.md`) |
| `needs` | no | Array of brief IDs that must complete before this brief runs |
| `tracks` | no | Brief ID whose output file tracks build progress (build briefs only) |

### Execution order

The `needs` dependencies form a directed acyclic graph. The `/spec:define` skill resolves the topological order by calling `specify schema pipeline define --change <dir>`, which returns the briefs in dependency-safe order. Skills execute each brief in sequence, reading the artifacts generated by earlier briefs.

For example, the Omnia define pipeline resolves to:

```text
proposal → specs → contracts → design → tasks
```

The Vectis define pipeline adds `composition` between `contracts` and `design`:

```text
proposal → specs → contracts → composition → design → tasks
```

## Schema composition

Schemas can extend other schemas using the `extends` field. A child schema inherits the parent's pipeline entries and brief files, overriding only what it explicitly declares.

```yaml
extends: https://github.com/augentic/specify/schemas/omnia
```

When a brief file is missing from the child schema's `briefs/` directory, the resolution algorithm falls back to the parent schema's directory. This allows a child schema to override only the briefs that differ.

## Schema resolution

Projects reference their schema in `.specify/project.yaml`:

```yaml
schema: https://github.com/augentic/specify/schemas/omnia
```

Schema URLs support an optional `@ref` suffix to pin a specific git ref:

```text
https://github.com/augentic/specify/schemas/omnia@v1
```

The CLI resolves the schema to a local directory by checking `.specify/.cache/` first (populated at `/spec:init` time) and fetching from the remote if needed. See [Configuration Files](../reference/configuration.md) for the full resolution algorithm.

## Adding or modifying a schema

1. **Create the directory** under `schemas/<name>/` with a `schema.yaml` and a `briefs/` subdirectory.

2. **Declare the pipeline.** List the define, build, and merge phases with their brief entries. Add a `plan` phase if the schema supports Layer 3 initiative authoring.

3. **Write the briefs.** Each brief needs YAML frontmatter with at minimum `id` and `description`. The `needs` array declares dependencies on other briefs. The body contains the agent instructions for that pipeline stage.

4. **Validate.** Run `make checks` -- the `checks.ts` script verifies:
   - `schema.yaml` validates against `.cursor/schemas/specify-schema.schema.json`
   - All `brief` paths resolve to existing files
   - Brief frontmatter `id` matches the pipeline entry `id`
   - All `needs` references point to declared brief IDs
   - The `needs` graph contains no cycles (Kahn's algorithm)

5. **Register in the README.** Update `schemas/README.md` with the new schema's entry.
