# Decisions

Standing architectural decisions for the `specify` CLI. Read before changing error layering, exit codes, atomic writes, or the YAML library.

Each entry records the decision, why it was taken, and the consequences a change must reckon with — not how the feature works today. Current behavior lives in [`docs/standards/workflow.md`](./docs/standards/workflow.md) (the workflow contract), [`docs/standards/architecture.md`](./docs/standards/architecture.md) (workspace shape), and module-level rustdoc; entries here point at those rather than restating them.

## Error layering

`specify-error` is the dependency leaf of the workspace. It depends only on `thiserror` and `serde-saphyr`; every other `specify-*` crate may depend on it, and it depends on none of them. The leaf stays free of rich domain payloads: `Error::Validation { code, detail }` is payload-free (see [§"Drained `Error::Validation` and the `Diagnostic` substrate"](#drained-errorvalidation-and-the-diagnostic-substrate)) — the top-level wire `error` is the carried `code` discriminant, and rendered findings travel on stdout as a `DiagnosticReport`, not inside the error.

## Exit codes

The binary commits to a four-slot exit-code table. `Exit::from(&Error)` in `src/runtime/output.rs` is the single source of truth; every dispatcher routes its error through it. `Exit::Code(u8)` is reserved for the guest leg's exit-code passthrough.

| Code | Name                      | When                                                                                                                            |
| ---- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 0    | `EXIT_SUCCESS`            | Command succeeded.                                                                                                              |
| 1    | `EXIT_GENERIC_FAILURE`    | Any `Error` variant not listed below (I/O, YAML, schema, merge, tool resolver/runtime, ...).                                    |
| 2    | `EXIT_VALIDATION_FAILED`  | Validation findings, `Error::Validation`, `Error::Argument`, or a tool request rejected as undeclared.                          |
| 3    | `EXIT_VERSION_TOO_OLD`    | `project.yaml.specify` is newer than `CARGO_PKG_VERSION`.                                                               |

`Exit::ArgumentError` and `Exit::ValidationFailed` are distinct Rust variants that share code `2`, keeping the wire contract four-slot while preserving dispatcher-side clarity — anything actionable by the operator is in the JSON envelope's `code` discriminant, and per-finding detail is on the stdout `DiagnosticReport`.

A pin **newer** than the binary is exit `3` (`Error::CliTooOld` — the binary must catch up). A pin *older* than the binary loads fine: pre-1.0 there are no compatibility shims and no migration framework — a major cut means re-init, not migration (see [§"Bootstrap and upgrade lifecycle"](#bootstrap-and-upgrade-lifecycle)).

Lint is the one finding-driven exit slot (today `specify lint framework`; `lint project` retired from the operational surface): it returns `2` only on a finding with `status: open` AND `severity ∈ {critical, important}` — see [§"Lint finding status, disposition, and exit"](#lint-finding-status-disposition-and-exit).

## Atomic writes

Use `yaml_write` (in `crates/model/src/atomic.rs`) for any file a concurrent reader may observe mid-write: `plan.yaml`, `metadata.yaml`, and the registry. It serialises to `NamedTempFile::new_in(parent)` and `persist`-renames over the target so readers either see the prior bytes or the new bytes. Plain `fs::write` is reserved for files no other process reads concurrently with the writer (one-shot scratch output, fixtures inside a tempdir test).

## YAML library

The workspace uses `serde-saphyr` (pinned to a `0.0.x` release) for both deserialization and serialization. It is pure-Rust, panic-free, and actively maintained, in contrast to `serde_yaml` (deprecated) and `serde_yaml_ng` (community fork carrying the same debt). Saphyr omits a `Value` DOM, so code that needs untyped YAML access deserializes into `serde_json::Value`. Its separate deser/ser error types ride directly on `specify_error::Error::YamlDe` and `Error::YamlSer` (both `#[error(transparent)]` `#[from]` variants), so `?` on a raw `serde_saphyr` result still propagates and the kebab discriminant on the wire stays `yaml` for either side.

## Diag-first error policy

`Error::Diag { code, detail }` is the default for new diagnostics. A typed `Error::*` variant exists only when (a) a test or skill destructures the variant's payload, (b) the variant routes to a non-default `Exit` slot, or (c) three or more call sites share the exact shape. The kebab `code` is the wire contract; the Rust variant is for callers that pattern-match. See AGENTS.md §"Errors" for the full rule.

## Hint colocation

Long-form recovery hints live on `Error::hint(&self) -> Option<&'static str>`, not on the renderer. `ErrorBody::render_text` calls it. Adding a new hint means extending `Error::hint`, not the renderer. Hints for collapsed `Diag` codes are looked up by the kebab `code` so a `Diag` site without a typed variant can still surface guidance.

## Wire compatibility

The CLI's JSON output is a flat envelope: every successful body is the typed `*Body` rendered directly, every failure body is `ErrorBody`. Skills grep on the `error` / `code` discriminants; tests assert on them. There is no top-level `envelope-version` integer — re-introduce one only if a breaking shape change ships and consumers need a version stamp to refuse output they cannot parse.

The kebab-case `code` discriminant on `Error::*` variants is the public contract: renaming or removing one is breaking; adding a fresh one is additive. CLI **input** flags are a peer wire surface under the same rules — adding an optional flag is additive, removing or renaming a flag is breaking. One non-additive input change has shipped: `specify init` enforces the `<adapter>`-with-`--workspace` conflict through clap, while a *missing* adapter falls through to the RFC-65 elicitation layer in the native handler — a line prompt when stdin is a TTY, the typed `init-adapter-required` (`Error::Validation`, exit 2) everywhere else (the historical `init-requires-adapter-or-workspace` discriminant survives in `crates/workflow/src/init/` as the defence-in-depth check for embedders).

## Shell completions

`specify completions <shell>` writes a clap-generated completion script to stdout for any shell `clap_complete::Shell` covers. The script is a pure function of the live clap surface, so verb additions/removals are auto-tracked without extra plumbing.

## Crate layout

The crate graph (leaf → root, with per-crate roles) is pinned in [AGENTS.md §"Crate graph"](./AGENTS.md) and [architecture.md §"Workspace layout"](./docs/standards/architecture.md#workspace-layout); this entry records why the shape is what it is.

SHA-256 digest encoding lives in `specify_schema::digest` (the `specify-schema` leaf), so siblings such as `specify-standards` and `specify-diagnostics` share one digest implementation without depending on `specify-registry` (and therefore Wasmtime). `specify-model` exists so the artifact types and parsers sit on a lifecycle-free leaf; it also holds the artifact validation rule registry (`specify_model::validate`) and depends on neither `specify-workflow` nor anything named lint, so a validation rule physically cannot reach a slice transition or plan stamp — the same no-lifecycle-authority invariant `specify-standards` enforces. The init-time `AGENTS.md` context-fence generation lives in `specify_workflow::agents`, whose only consumer is the root binary.

No framework `CORE-*` rule uses the deleted `specify_standards::framework` `Check` substrate — every rule resolves through the generic lint dispatcher, with Road B checkers running in-process under `crates/standards/src/lint/framework_tools/`; see [§"Framework lint engine: generic dispatcher (Road A / Road B)"](#framework-lint-engine-generic-dispatcher-road-a--road-b). The former `Check` substrate (trait, `Context`, `builder.rs`, helpers) is deleted: its only live content was the repo-local Rust-quality predicates, which now live dev-only beside their single consumer at `tests/rust_quality/checks.rs` in the root crate, and the brief path-classification, which `crates/standards/src/lint/index/brief.rs` owns.

### New workspace crates

New functionality lands in an existing module by default. A new workspace crate requires a paragraph in this file justifying why an existing module cannot host the code, and what dependency-direction invariant the new crate enforces (which leaf-→-root edge it preserves, and which existing crate would have grown a cycle). A new crate that does not strengthen the dependency direction is overhead; refactor within an existing module instead. Adapter-specific logic never lands as a workspace crate — it lands in the adapter's WASI carve-out.

## Integration tests: one binary per crate, `#[path]` submodules

**Decision (2026-06, supersedes "one binary per area").** Each crate exposes exactly **one** integration binary, `tests/it.rs`, which pulls every area in as a `#[path]` submodule (`#[path = "plan.rs"] mod plan;`). The per-area files stay on disk and keep their own `#[path = "<area>/<concern>.rs"]` sub-includes, so the directory layout is unchanged — only the *target* boundary moves. Each crate sets `autotests = false` and declares its `it` (and the standalone `rust_quality` dev gate) explicitly under `[[test]]`. The shared helper is declared once at the `it.rs` root (`mod common;` / `mod eval_support;`) and every area reaches it as `crate::common`; merges never cross crate boundaries, so `specify`, `specify-workflow`, `specify-standards`, and `specify-schema` each own a distinct `it`.

The crate-under-test links once per crate instead of once per area — that link, not test LOC, is the integration suite's build cost, and the always-run suite was throttled by binary count. The earlier per-area decision rejected a *single workspace-wide* `tests/it.rs` (7.3 % cold-build win, below the 20 % bar, and a mega-binary kills `cargo test --test <area>`). One binary **per crate** keeps that objection answered: `cargo test -p <crate>` still scopes to a crate, and nextest's `-E 'test(<area>::)'` module filter restores per-area selectivity inside the `it` binary, so local iteration does not regress.

**Measured (2026-06).** ~30 integration binaries → 5 (`specify::it`, `specify-workflow::it`, `specify-standards::it`, `specify-schema::it`, and `specify-model`'s single `atomic`), with `rust_quality` remaining a standalone dev-gate binary. The full workspace — 1,751 tests — runs in ~18 s under `cargo nextest run --workspace` at the default 4-wide pool. Goldens refresh through the module filter (`REGENERATE_GOLDENS=1 cargo nextest run -E 'test(e2e::)'`). The subprocess test-groups in [`.config/nextest.toml`](./.config/nextest.toml) pin to `binary_id(specify::it)`, since only the root `it` forks `specify` children and JIT-compiles WASI fixture components; the crate-level `it` binaries are in-process.

## Unit tests: minimized, coverage-gated

**Decision (2026-06).** The unit layer is kept deliberately thin. Integration (binary + crate `tests/`) owns every CLI-reachable behavior; a `#[cfg(test)]` unit test survives only when it covers a branch genuinely unreachable through the CLI, or is the cheap home for a dense parse/projection edge matrix whose case-per-cell integration port would inflate the 4-wide subprocess pool ([`.config/nextest.toml`](./.config/nextest.toml)). This supersedes the implicit "kernel matrices live unit-side" stance; it composes with the binary-layout decision above (one binary per crate).

Two mechanics make aggressive reduction safe:

- **Collapse, don't enumerate.** A unit test that walks a closed `(input → code)` set is one table-driven `#[test]` with a block per case, not one `#[test]` per case. The 2026-06 sweep collapsed five workflow matrices this way — `config` (24 → 12), `adapter/core` (24 → 9), `build/wire` (24 → 11), plan `validate` (31 → 13), and `propose` (34 → 23), −69 test fns — with **zero** `cargo llvm-cov` line/region movement (the crate held 75.18 % line / 74.77 % region byte-identical across the sweep).
- **Coverage is the brake.** `cargo llvm-cov nextest -p <crate> --summary-only` runs before and after a reduction; a `TOTAL` drop on still-live lines blocks the deletion until an integration assertion backfills it. Coverage, not case count, is the invariant. `nextest` (not bare `cargo test`) is mandatory — its per-test process isolation is what lets the CWD/env-mutating suites pass, and it is the runner CI uses.

## Framework lint engine: generic dispatcher (Road A / Road B)

**Decision (2026-06).** The `specify lint framework` engine is a generic, rule-agnostic dispatcher carrying **no rule-specific check logic and no rule policy**. Every framework `CORE-*` check resolves through one of two roads, and `specify` (the framework repo) owns both the checks and the values they enforce:

- **Road A — declarative hint.** The rule carries a `kind:` ∈ `schema | reference-resolves | constant-eq | unique | fenced-block | regex | path-pattern | presence | field-grammar`, interpreted by a generic per-kind evaluator in `crates/standards/src/lint/eval/*` over `WorkspaceModel` facts. `hint.value` names the mechanism selector and `hint.config` carries the policy. The per-kind selector semantics live in the eval modules' rustdoc and [AGENTS.md §"Crate graph"](./AGENTS.md) (`crates/standards/src/lint/` bullet).
- **Road B — referenced tool.** The rule carries `kind: tool, value: <tool>` plus a sentinel `path-pattern`. `lint/eval/tool.rs` resolves the tool **by name**, runs it once per lint, and folds its findings (stamped with the tool's own `rule_id` / `severity`; the engine restamps only `id` / `fingerprint`). For framework lint the inventory is the in-process `framework_tools` checker table in `specify-standards` (described below), called directly for typed findings; for project lint the name routed through the `ToolRunner` trait to the declared WASI tool inventory, whose `DiagnosticReport` stdout the evaluator parsed (historical — `lint project` retired from the operational surface with RFC-65; the trait survives as the evaluator's seam).

**Policy lives in the rule's `config:`**, in `specify`. Road A reads it directly; Road B has it forwarded as a second positional argument — the engine relays, it never interprets. Enforced permanently by the Layer-3 guard test [`crates/standards/tests/lint_engine_guards/no_embedded_policy.rs`](./crates/standards/tests/lint_engine_guards/no_embedded_policy.rs), which fails if any eval arm reintroduces a rule-specific literal. The only engine-side constants left are mechanism (evidence-size / snippet / iteration bounds).

**There is no `kind: authoring-predicate`.** The engine carries no imperative rule predicates and no duplicated owner maps; all policy rides the rule's `config:`.

**Five framework checkers run in-process.** The Road B framework checkers (`scenarios`, `links-registry`, `marketplace`, `prose`, `rules`) are native Rust modules under [`crates/standards/src/lint/framework_tools/`](./crates/standards/src/lint/framework_tools.rs), beside the engine in `specify-standards`. The `kind: tool` evaluator resolves a checker name against the `framework_tools` inventory (`is_framework_checker` / `run_checker`) before the `ToolRunner` trait is consulted, calling it directly and folding the typed `Diagnostic` findings — no `ToolRunner` hop and no JSON serialise→reparse round-trip. Each checker receives `(candidate-path, config-json)` argv, reads policy only from the rule's forwarded `config:`, and returns findings the evaluator restamps (`id` / `fingerprint`): `requested_rule` matches the candidate filename exactly; the prose checker parses `description.maxLength` from the canonical embedded skill schema; a missing project dir surfaces findings instead of silently passing. The `ToolRunner` trait (and `NoopToolRunner`, which backs the framework surface) survives only as the evaluator's seam — the WASI impl retired with `lint project`. The adapter validators (`contract`, `vectis`) are in-guest library code inside their published components, not lint-dispatched tools.

Test coverage rests on the per-kind evaluator unit suites (`crates/standards/src/lint/eval/*`), the `no_embedded_policy` guard, the schema byte-match gate (`crates/schema/tests/schemas.rs`), and each checker module's unit tests.

**The lint residue is native-forever (RFC-61 Step 5, Milestone S7 — 2026-07).** The lint shrink deleted every `CORE-*` check whose consistency burden moved into the type system or the WIT contract: the cli-contract family (CORE-057/060, with the `specify contract dump` verb, the `CliContract` DTO, and the root `build.rs` tests-inventory embed), the skill-body / orchestration family (CORE-005/023/037/039/040/041/045/046/047/048/050), the operational-vocabulary check (CORE-025), the adapter-manifest family (CORE-001/006/010/061 in this milestone; 004/007 pre-deleted), and the guardrail-citation check (CORE-063). Their orphaned evaluator kinds (`cardinality`, `set-coverage`, `cross-reference`, `cli-contract`), the `skill-body` / `extension` Road B checkers, the `adapter_manifest` / `adapter_dir` fact families, and the manifest-policing indexer extractors went with them; adapter-manifest shape is enforced at resolve time by the engine's per-axis schemas (the deeper RFC-64 handoff — manifest resolver retirement, `pack_adapter` transport — is deferred to S8). What survives — authoring house style, link resolution, marketplace and scenarios consistency — runs **only** as native Rust in the root workspace under `make lint`, never as a guest: `specify lint framework` is host-side tooling for this repo's own prose. Judgment-prose link resolution additionally moved to compile time: `crates/workflow/build.rs` inlines and link-checks the embedded corpus, so a dangling reference fails the build.

## Extension architecture

`specify-registry` owns the WASI tool cache + resolver, the Wasmtime-backed execution host, and the RFC-48 OCI transport plus content-addressed adapter store, deliberately independent of the adapter loader. Post-S4 (see §"Old-stack deletion") the crate has exactly two consumers: `adapter build/publish` + `init` drive `pack` / `oci` / `store`, and `lint project`'s `kind: tool` evaluator drives `resolver::resolve` → `host::WasiRunner` for project-scope tools. The `extension run/fetch/gc/schema` verb family and adapter-scope extension declarations are gone. **Amendment (RFC-64/RFC-65):** the consumer list above is historical — `pack` and the raw-OCI tree layer retired with the one-component artifact (see [§"One component, no manifest (Milestone R64-S)"](#one-component-no-manifest-milestone-r64-s)), the `adapter build/publish` verbs retired to the adapters repo's scripted workflows, and `lint project` retired from the operational surface. What survives today: `package.rs` (the wasm-pkg client funnel), `store.rs` (the global single-file adapter store behind `install_tofu`, driven by the hydration triggers), and `host.rs` + `resolver` + `permissions` (the declared-tool runner, orphaned by the `lint project` retirement and kept only until the `tools[]` surface's fate is decided). The manifest DTOs (`Extension`, `ExtensionSource`, `ExtensionPermissions`, `ExtensionScope`, …) and their structural validation live in the wasmtime-free leaf `specify-extension`, re-exported by `specify-registry` under the `manifest` / `validate` module paths — the split keeps `wasmtime` out of `specify-workflow`'s compile graph (workflow depends on `specify-extension` only). The standing policy choices:

- **Declaration site.** One scope: a `tools[]` array in `.specify/project.yaml`, each entry `{ name, version, source, sha256?, permissions? }`, validated by `extension.schema.json`. Adapter manifests carry no extension declaration — adapter tooling is in-guest library code.
- **Cache layout.** Root resolves `$SPECIFY_EXTENSIONS_CACHE` → `$XDG_CACHE_HOME/specify/extensions/` → `$HOME/.cache/specify/extensions/`; scope segments and the `--` separator are pinned in [architecture.md §"WASI tool sidecar scope"](./docs/standards/architecture.md#wasi-tool-sidecar-scope). The wasmtime compilation cache lives beside the scope dirs at `<root>/wasmtime/` (override: `$SPECIFY_WASMTIME_CACHE`); it is best-effort.
- **Sidecar invalidation.** The cache sidecar (`extension-sidecar.schema.json`) records `(scope, tool-name, tool-version, source, fetched-at, permissions-snapshot)` plus optional `sha256` / `package`; any mismatch with the live declaration forces a refetch via atomic move. When `sha256` is present, fetched bytes are verified before installation. Permissions changes alone never invalidate the cache — permissions are evaluated per run.
- **Permission substitution.** `$PROJECT_DIR` substitutions apply only inside `permissions.{read,write}` (not module argv). After substitution paths must be absolute, free of `..`, and canonicalise inside the granted root. `write:` entries targeting Specify lifecycle state (`.specify/`) are rejected by both the schema and the runner.
- **Wasmtime configuration.** Pin `wasmtime` / `wasmtime-wasi` to a matching stable pair, use the synchronous WASI Preview 2 path and `component::Component`, and disable filesystem access by default — preopens come from declared permissions only. Execution stays behind the concrete runner boundary in `crates/registry/src/host.rs`.
- **Registry resolution.** Wasm-pkg config is layered, last-write-wins: global defaults → project-local `.specify/wasm-pkg.toml` → `WKG_CONFIG` → an embedded `specify -> augentic.io` namespace fallback. `specify init` scaffolds the checked-in `.specify/wasm-pkg.toml` and never overwrites an operator-edited file. RFC-48 adapter packages transit a single content-addressed OCI layer rather than the wasm-pkg package path (see [§"RFC-48 adapter store and transport"](#rfc-48-adapter-store-and-transport)).
- **Time crate.** UTC-only domain on `jiff::Timestamp`; all persisted stamps route through `specify_error::serde_rfc3339` so the wire shape stays `%Y-%m-%dT%H:%M:%SZ` byte-for-byte.

## Guest-to-guest transport: wRPC behind the dispatch seam

**Decision (2026-06).** All guest-to-guest dispatch — every host-mediated `source` / `target` call (the runtime move, RFC-56), local or remote — is carried over [wRPC](https://github.com/bytecodealliance/wrpc), the Bytecode Alliance's WIT-native, transport-agnostic component RPC. Only the transport varies by deployment: an in-process or Unix-domain-socket transport co-located on one node, NATS or QUIC across a cluster. wRPC encodes the typed `augentic:specify` records (and their async `stream` / `future` values) from the same WIT the binding generator consumes. Why: the project exists to scale from desktop to cloud without changing guest or host code, and a single dispatch path whose transport is config delivers exactly that — cloud is a transport swap, not a code-path change — with wasmCloud proving this brokered peer-to-peer model at scale. The earlier dual-path design (native in-process locally, wRPC only across nodes) is superseded: it special-cased the local hot path and duplicated dispatch for a serialization cost that is negligible against `build` / `merge` (model eval + compile dominate) and tolerable on the frequent calls.

Consequences a change must reckon with:

- **The seam, not the transport, is the contract.** The per-axis imports (`source` / `target`) are the durable boundary; the `specify:adapter` package (named `augentic:specify` when this was decided) names no transport. wRPC is a swappable backend behind it, so a native in-process lift/lower fast-path can be dropped in behind the same seam if profiling ever shows the high-frequency callbacks (`eval -> resolve`, `survey` / `extract` fan-out) need it — without touching guests or the contract.
- **Resources do not cross — uniformly.** wRPC carries WIT resources only as opaque, application-defined handles, so a live `wasi:filesystem` `descriptor` (inside `working-tree`) is never transported. `build` / `merge` always ship the content-addressed `revision` / `changeset` and the serving node re-materializes its own tree (the working-tree backend, RFC-55) — the same flow local and remote, with the descriptor always node-local. `survey` / `extract` / `guidance` exchange plain records.
- **Pre-1.0 dependency on the universal hot path.** wRPC and its transport crates are pre-1.0 (Apache-2.0 WITH LLVM-exception); it now sits on every call, not just the cross-node leg, so the risk is concentrated and the seam (native fast-path in reserve) is the mitigation. Pin wRPC and track its Wasmtime pin against the runtime's. Prefer `wrpc-transport` + `wit-bindgen-wrpc` server bindings wired to the existing multi-guest instance-per-call registry over adopting `wrpc-runtime-wasmtime` (which would cede instantiation and add a second Wasmtime pin).
- **Async everywhere.** wRPC is async (Tokio), so guest-to-guest dispatch is async on every path; this aligns with the component-model-async / WASI 0.3 direction, which landed default-on in Wasmtime 46.0.0 (`component-model-async` + WASI 0.3.0 enabled by default), with the broader async ABI still filling in incrementally. **46.0.0 is therefore the runtime floor for this dispatch path.** Instance-per-call is unchanged: each invocation is served by a fresh instance from the registry, so the multi-guest single-binary registry holds — and *recursive* reentrance (an `eval -> resolve` callback into a live instance) still traps, so the callback lands in a fresh instance; only *sibling* reentrance is allowed.

## Guest execute loop (RFC-61 Step 4, Milestone E)

**Decision (2026-07).** The drained execute loop ports into the workflow guest as `specify plan execute` → `specify_workflow::orchestrate::execute` — the `/spec:execute` skill's body as control flow: `plan status` projection → `plan next` claim → refine / build / merge until `drained` or a typed stop. Standing choices:

- **Argv.** `plan execute` lives in the shared clap grammar (one `--help`), but the native binary refuses it with the standard argument error (wire code `argument`, exit 2) — the mirror image of the guest's native-only refusals. Natively the loop stays skill-owned until Step 5.
- **Refine orchestrator.** `orchestrate::refine` composes the native critical path verbatim: `slice create --if-exists continue` → per-binding extract fan-out → seam-guided synthesis judgment → the shared persist tail (`specify_workflow::slice::synthesis::persist`, the same code the retired `slice synthesize --from` ran) → the `slice validate` gate sweep → `refined`. No new journal events — the loop composes the per-phase cadence (`plan.entry.advanced`, `slice.synthesize.*`, `slice.build.*`, `slice.merge.*`, transitions), so a journal reader cannot tell a drained execute run from the same phases driven one breakout at a time. A stop returns as a typed outcome carrying the status projection's closed `StopReason` + hint; the shim maps it to `plan-execute-stopped` (exit 2). Phase failures leave the entry `in-progress` (merge stays the only `done` writer) — re-entry safe.
- **D1 guest marker.** The loop holds a create-exclusive advisory marker at `<plan-root>/.specify/guest.lock` (`OpenOptions::create_new`; body pid / hostname / acquired-at as diagnostics only) for guest-vs-guest breakout refusal — a second in-guest execute fails `guest-marker-held` (exit 2). The marker is removed on guard drop; a crash that skips destructors leaves it behind and the next acquire tells the operator to delete it (no pid-liveness probe — WASI has no process table). **No cross-stack interlock is claimed**: the native flock (`plan_lock`) neither takes nor probes the marker; non-concurrent stack use is the documented coexistence rule. The native flock is untouched.
- **Single-project scope.** The loop refuses workspace-routed plans up front (`plan-execute-workspace-unsupported`, exit 2) — when the plan root is a workspace (`workspace: true`) or any entry carries a `project:` scope. The skill's workspace routing (slot sync + chdir into `workspace/<project>/`) has no in-guest counterpart yet; refusing beats silently creating slices under the workspace root's own `.specify/` tree. Workspace plans stay on the native skill-driven path.
- **Plan-next lock satisfaction.** The loop claims through the lock-free core `plan_next_body` (journalling `plan.entry.advanced` exactly as the native handler does) rather than the `require_held`-gated dispatch handler — the flock fences separate OS processes racing the plan, and the guest collapses every breakout in-process. At the time the native gate was not weakened; the flock and its `require_held` gates were retired at S4 (D-planlock — see §"Old-stack deletion").
- **Elicitation to argv.** `specify plan create --intent <string>` is pure sugar for `--source intent=intent:value:<string>`, desugared before the source-map build so combining it with an explicit `intent` binding trips the existing `plan-source-duplicate-key` gate.
- **Runtime model host.** Driving the judgment leg from the execute loop makes the workflow guest genuinely import `omnia:model/completion` (Milestone D's `Provider` implemented `Model` but no verb called it, so the component never carried the import). The `specify-runtime` binary and the composed-test bundle therefore bind `WasiModel: ModelDefault` (the replay backend — connects clean with no fixtures) so the deployment links; the operational cursor backend swap is RFC-61 §Step 2, not this milestone.

## Guest verb parity and native residue (RFC-61 Step 4, Milestone G)

**Decision (2026-07).** The Step 4 → Step 5 boundary is pinned by a full verb-parity audit: every verb in the shared clap grammar is classified **guest-owned**, **native residue until Step 5**, or **deleted at Step 5**, and every orchestration line in the eight `plugins/spec/skills/*` bodies is mapped to its guest home. The matrix and coverage map lived at `rfcs/rfc-61-step-4-parity.md` (completed and removed from the tree; recoverable from git history); this entry records the residue rule itself (decision D4):

- **The native residue set** — `init`, `upgrade`, `plugins`, `lint`, `workspace`, `registry`, `adapter`, `rules`, `catalog`, `archive`, `contract`, `completions`, `plan lock`, and the two-phase `slice build` handler — stays binary-side because each needs subprocesses, the network, Wasmtime, git, or host-machine state the guest deliberately does not model. The guest refuses every residue verb on the standard argument-error surface (wire code `argument`, exit 2) with a hint naming the native binary; no residue verb grows a guest shim "for parity".
- **Deleted at Step 5, never ported:** `extension run` (and its `fetch` / `gc` / `schema` cache verbs — the vectis and contracts tools are already in-guest adapter library code), the `--phase` flag on `source survey` / `source extract` / `slice build`, and the `--dry-run` / `--from` envelope pairs on `slice synthesize` and `plan propose`. Their behaviour already lives in the guest orchestrators; the envelope machinery is the thing the migration exists to remove.
- **The one failing skill is known and scoped.** Seven of eight skills pass the RFC's invoke-and-relay test today; `/spec:plan` does not — its propose judgment leg (`judgment::propose::reconcile`) and kernel exist but are unwired to any verb, `orchestrate::survey_all` has no dispatch verb, and the Gate 1 prose artifacts (`change.md`, `discovery.md` header sections) are outside the propose answer schema. The plan-authoring collapse is a documented Step 5 precondition, not a Milestone G build.

## Plan-authoring collapse: `plan author` (RFC-61 Step 5, Milestone S1)

**Decision (2026-07).** The `/spec:plan` critical path collapses into one guest orchestration, `specify plan author <name> [--source <key>=<adapter>:<binding>]... [--intent <string>]` → `specify_workflow::orchestrate::author`: scaffold (`plan create` semantics — same kebab gate, same `already-exists` refusal, same `--intent` desugar through the duplicate-key gate) → `survey_all` fan-out → `build_request` → `judgment::propose::reconcile` with check = `Plan::propose_from` against a throwaway clone plus the Gate 1 prose round-trip → the real projection under the atomic write loop → Gate 1 prose persistence → the `plan validate` doctor sweep → exit at `pending` with the literal `specify plan transition <name> approved` hint in the outcome envelope. Standing choices:

- **A new verb, not a `plan create` extension.** `plan create` keeps its native scaffold-only semantics on both stacks (skills and operators depend on "create writes an empty `slices:` list and exits"); overloading it would make one spelling mean two different flows per binary. `plan author` reads as the whole authoring act the ultrathin `/spec:plan` wrapper invokes ("elicit args → invoke → relay"), and follows the `plan execute` precedent: shared grammar, guest-dispatched, refused natively with the standard argument error (wire code `argument`, exit 2). No `--auto-approve` and no `--authority-override` on the author surface — Gate 1 stamping stays operator-only (the collapse exits at `pending` by design), and override pre-seeding needs slice rows that don't exist until the propose leg has run (post-author `plan amend` covers it).
- **Answer-schema widening.** The canonical `schemas/discovery/proposal.schema.json` response arm gains an **optional** `gate` object (`$defs.gateProse`: required `change`, `discovery-summary`, `discovery-source-inventory` strings) so native `plan propose --from` responses stay valid unchanged; the `answers.rs` derivation then makes `gate` **required** on the judgment answer, so the guest model call always carries the Gate 1 prose. The typed `ProposalResponse.gate: Option<GateProse>` is kernel-ignored — `Plan::propose_from` never reads it.
- **Gate 1 prose persistence is frame-deterministic, body-model.** The model authors section bodies only; the orchestrator owns every deterministic frame. `change.md` is written whole (`# Change — <name>` + the `change` body) via the shared atomic writer — the artifact has no parser, matching the native skill's free-form authoring. The `discovery.md` `## Summary` / `## Source inventory` sections land through a new validated writer, `Discovery::set_preamble`, which replaces the prose ahead of `## Lead inventory` and rejects (`discovery-preamble-invalid`) any preamble that breaks the parse round-trip — the lead inventory rides through byte-untouched. The prose check runs *inside* the reconcile repair loop, so a missing `gate` (`plan-author-gate-missing`) or a structure-corrupting preamble re-prompts instead of failing after the projection.
- **Plan context rides the user message, not the request envelope.** `reconcile` gains an optional `GateContext` (plan name + `plan.yaml.sources` bindings) rendered as a `## Plan context` section, so the model can author the source-inventory rows without widening the pinned `ProposalRequest` schema.
- **Journal cadence composes the native verbs'.** Per-source `source.execution.agent` / `source.survey.completed` pairs from the fan-out, then the single `plan.reconcile.completed` after the write commits. The native propose dry-run fires no journal event, so the judgment dispatch adds none — no new event ids.
- **Single-project scope.** A workspace plan root refuses up front (`plan-author-workspace-unsupported`, exit 2), mirroring the execute loop's D3 posture — workspace plans stay on the native skill-driven path until slot routing has an in-guest counterpart.

## D-refine breakout: `slice refine <name>` (RFC-61 Step 5, Milestone S1)

**Decision (2026-07).** Parity gap 2 closes with a standalone breakout verb, `specify slice refine <name>` → `specify_workflow::orchestrate::refine_breakout`, wrapping the existing `orchestrate::refine` for one named slice outside the execute loop. Guest-only; the native binary refuses it on the `plan execute` mirror surface (wire code `argument`, exit 2 — natively the phase stays `/spec:refine`-skill-owned until the thinning).

- **No claim, no advance.** The breakout mirrors the standalone `slice build <name>` posture documented in the parity audit: it acts on the named slice directly against a `pending` or `in-progress` plan entry and never writes per-entry status — `plan next` stays the only `in-progress` writer, so a breakout refine leaves the entry exactly where it found it. The only guard is terminal: a `done` entry refuses with `slice-refine-entry-done` (hint names `plan transition <entry> --undo`).
- **Target resolution is caller-free.** The loop hands `refine` the target from its `plan next` claim; the breakout resolves it itself — the slice's own `metadata.yaml` when the slice directory already exists (a resumed `refining` breakout), else the bound project's topology via `resolve_target`, failing as `slice-create-target-missing` (the execute loop's code for the same miss).

## Manifest-schema relax: two-shape coexistence window (RFC-61 Step 5, Milestone S2)

**Decision (2026-07).** `briefs` and `execution` drop out of the top-level `required` lists of `adapter.schema.json`, `source.schema.json`, and `target.schema.json` — requiredness only; every property definition stays, and a manifest that *does* carry `briefs` is still held to the full per-axis key set (`extract` + `survey` / `shape` + `build` + `merge`). This is a deliberate coexistence window, not the end state: the adapters repo is about to shrink its eight manifests to post-cutover fields only (`name`, `version`, `axis`, `description`, and vectis's `platforms`) because nothing reads manifests for agent handoffs after the cutover, while this branch's composed runtime tests, eval driver, and native two-phase verbs keep resolving both shapes through the same `SourceAdapter::resolve` / `TargetAdapter::resolve`. The final property removal (deleting `briefs` / `execution` / `prepare` and the rest of the handoff machinery from the schemas outright) landed with the machinery deletion in Milestone S4 (see §"Old-stack deletion") — the window is closed and the bullets below are historical.

- **Typed representation.** The manifest structs keep their existing field types with `#[serde(default)]`: absent `briefs` is the empty map (a literal empty `briefs: {}` cannot reach the loader — the per-axis schemas require the full key set whenever the property is present), absent `execution` stays `None`. No new wrapper types.
- **Operation-set derivation.** For a briefless manifest, `operations()` falls back from `briefs.keys()` to the axis's closed WIT operation set (`wit/specify.wit`: source = extract/survey, target = guidance/build/merge with `shape` the manifest spelling of `guidance`) — the same set the full `briefs` key set equals by schema, so full-shape manifests iterate exactly as before.
- **Point-of-use refusal, not resolve-time.** The resolve-time `check_execution` gate is deleted; consumers that need the missing machinery refuse with a typed error where they consume it: the shared source prep seam (`source survey` / `extract` / `preview`) raises `adapter-briefs-missing`, and the native `slice build` dispatch raises `adapter-execution-mode-required` before any side effect (no request write, no `target.execution.agent` emit). Full-shape manifests are behaviorally untouched.

## One `specify` binary: triage main over `omnia::run` (RFC-61 Step 5, Milestone S3, decision D-bin)

**Decision (2026-07).** The root `specify` binary is the one operational binary: its `runtime::run` parses the shared clap grammar once, then triages — the guest-owned verbs (`plan execute`, `plan author`, `slice refine`: exactly the collapsed orchestrators the native handler table refuses with `argument`/exit 2) route to the composed deployment through `src/runtime/commands/guest.rs`, and every other verb dispatches in-process through today's handlers unchanged. The separate cursor-bound `specify-runtime` binary is deleted; `specify-runtime` becomes a library crate exposing the hand-rolled host surface (`CursorBundle`, `Hooks`, `drive`) the binary consumes. **Amendment (RFC-65 move 5):** the triage main is retired — the binary no longer parses the shared grammar, no native workflow-verb handler survives, and every non-provisioning argv forwards unparsed to the workflow guest; see [§"The provisioning front (RFC-65 move 5, amending D-bin)"](#the-provisioning-front-rfc-65-move-5-amending-d-bin). The transient per-invocation manifest assembly below is likewise retired in favour of the generated deployment manifest (see [§"Adapter hydration, the committed lock, and the generated deployment (RFC-65)"](#adapter-hydration-the-committed-lock-and-the-generated-deployment-rfc-65)); the bullets below are historical except where a later entry carries them forward.

- **Hand-rolled wiring, not the `runtime!` macro.** The macro emits its own private `main` (clap `Run` grammar included) and cannot be wrapped by a triage layer, so the crate implements the equivalent by hand over omnia's public surface: `CursorBundle` (`Backends` over `HttpDefault` + `OtelDefault` + the `omnia-cursor` client) and `Hooks` (`Wiring` linking `wasi:http` / `wasi:otel` / `wasi:model`, serving the HTTP trigger as the only long-lived server). `drive` blocks on its own multi-thread Tokio runtime around `omnia::run` in command mode and returns the guest's exit status (low byte) for process passthrough — the synchronous dispatch layer calls it like any other handler. The replay sibling (`specify-runtime-replay`, `ModelDefault`) keeps the macro; it never needs triage. **Amendment (RFC-65):** the premise expired — `omnia::runtime!` now also generates a public sync `drive` beside `main`, so the macro is mountable in-process and the hand-rolled wiring is gone; see [§"In-process host mount (RFC-65 move 2, amending D-bin)"](#in-process-host-mount-rfc-65-move-2-amending-d-bin).
- **The triage set is the natively-refused set, not the full parity-matrix guest-owned set.** S3 keeps both stacks working: the pure verbs and the two-phase orchestrator verbs (`source survey`, `source extract`, `slice build`, `slice merge run`) still have operational native handlers the current skills drive, so routing them to the guest here would change behavior before the S4 machinery deletion. Flipping those verbs guest-side is S4's move, in the same change that deletes the envelope machinery — the triage predicate (`guest::owned`) is the one place that widens.
- **Deployment manifest: project-root `omnia.toml` wins; otherwise transient assembly.** `init` does not materialize a manifest (a committed manifest would go stale against the adapter set and cache state), so the guest leg assembles one per invocation in a temp dir: the embedded workflow guest (see §"Workflow-guest distribution"), the discovered adapter guests (below), each routed at `/mcp/<name>`, and the working directory as the writable `"."` mount. Host paths are emitted as escaped TOML basic strings so a `\` or `"` in a path cannot break the manifest parse. An operator-provided `omnia.toml` at the project root replaces the assembly wholesale (the eval driver and composed tests use this to pin fresh-built guests).
- **Adapter-guest discovery = bound-adapter resolution first, directory scan second.** The project's bound adapters — the `project.yaml` `adapter:` target and every `plan.yaml` `sources.<key>` binding — resolve through the same `SourceAdapter::resolve` / `TargetAdapter::resolve` the workflow uses (store → cache → in-repo, verify-on-read included), and the guest is `<resolved-dir>/guest.wasm`; this is the only leg that reaches the RFC-48 store, because store entries key on the pinned `(name, version)` a binding carries. Adapters not (yet) bound — `plan author` runs before `plan.yaml` exists — are picked up by a name-only directory scan of the manifest cache then the in-repo `adapters/` tree per axis, first hit per `(axis, name)` winning; no adapter names are special-cased. Either leg finding an adapter directory (an `adapter.yaml`) without a committed `guest.wasm` beside it raises a typed `guest-runtime-failed` error instead of silently omitting the guest.
- **Failure surfaces split at the guest boundary.** A failure before or around the guest run — staging, deployment assembly, backend connect (`cursor-agent` missing from `PATH`) — renders the host-side `guest-runtime-failed` envelope (exit 1). Adapter-resolution failures during assembly are the one carve-out: they keep their own typed codes (`adapter-not-found`, `adapter-digest-mismatch`, `adapter-cli-too-old`, …) with their native exit semantics, so the operator sees the same diagnostics the native resolvers raise. A failure inside the guest is not wrapped: the guest renders its own envelope on the standard streams and its exit code passes through verbatim, so skills see one exit-code contract across both legs. `--plan-dir` is refused on the guest leg when it names anywhere but the working directory (`argument`, exit 2) — the guest anchors plan artifacts at the `"."` preopen, so any other plan root would be silently ignored (see the Step 4 parity ledger).

## Workflow-guest distribution (RFC-61 Step 5, Milestone S3, decision D-dist)

**Decision (2026-07).** The workflow guest ships **inside the binary**: the release-built component is committed at `crates/workflow-guest/guest.wasm` (~10 MB, refreshed by `cargo make dist-guest`) and embedded via `include_bytes!` as `specify_runtime::WORKFLOW_GUEST_WASM`; the triage guest leg stages the bytes into its transient deployment. Adapter guests are *not* embedded — the guest leg resolves each bound adapter through the axis resolvers (RFC-48 store → manifest cache → in-repo) and scans the cache/in-repo roots for unbound ones (see §"One `specify` binary"), because the adapter set is project-configuration, not binary identity. **Amendment (RFC-65 move 4):** the embed mechanism is retired wholesale — the committed artifact, its sidecar, the `tests/dist.rs` gate, the `dist-guest` task, and the `WORKFLOW_GUEST_WASM` payload are deleted; the core is resolved by the binary's own version instead. See [§"Core versioned by the binary (RFC-65 move 4, amending D-dist)"](#core-versioned-by-the-binary-rfc-65-move-4-amending-d-dist); the bullets below are historical.

- **Committed artifact over build-graph coupling.** Embedding a *freshly built* component would make every native `cargo build` depend on a `wasm32-wasip2` cross-build (a `build.rs` cargo-in-cargo recursion, or an external orchestration step every workflow — tests, `cargo install`, rust-analyzer — must know about). Committing the release artifact keeps the native build graph flat and follows the adapters-repo precedent (eight committed `guest.wasm` files); the cost is a documented regeneration step (`cargo make dist-guest`) when guest-reachable code changes, the same discipline the adapters repo already carries. The composed integration tests keep self-building the *debug* guest from source, so a stale committed artifact diverges from tested behavior only in the shipped binary.
- **Staleness gate: recorded-hash sidecar, not rebuild-and-compare.** A CI rebuild-and-byte-compare is out — wasm builds are not byte-reproducible across toolchains and a release cross-build per CI run is disproportionate cost. Instead `cargo make dist-guest` records a sidecar at `crates/workflow-guest/guest.wasm.sha256` carrying two SHA-256 digests: `wasm:` (the committed component's bytes) and `sources:` (a deterministic fingerprint over the guest build graph — the `src/` tree + `Cargo.toml` of every workspace crate in the guest's dependency closure, plus the repo-root `wit/` and `schemas/` trees the guest embeds). The `tests/dist.rs` integration test — in the ordinary suite, so `cargo make ci` runs it — recomputes both and fails on either drift: a hand-edited or corrupted `guest.wasm` trips `wasm:`, and editing guest-reachable source without re-running `dist-guest` trips `sources:`. Regeneration is only via `cargo make dist-guest` (rebuild, copy, then `REGENERATE_GOLDENS=1` over the dist test), so the sidecar can never record a fresh source fingerprint against a stale component. Known boundary: external dependency bumps (`Cargo.lock`) and toolchain changes are not fingerprinted — the release checklist in `docs/release.md` keeps the human judgment step for those.
- **Embed over loose file.** `include_bytes!` of the committed artifact (rather than shipping `guest.wasm` beside the binary) keeps the release a single self-contained executable — no install-layout probing, no version-skew window between a binary and a sidecar file. The ~10 MB size lands the release binary well under the existing archive-workflow limits.

## Release identity (RFC-61 Step 5, Milestone S3, decision D-release)

**Decision (2026-07).** The `specify` package is `publish = false`: it cannot go to crates.io while the omnia stack rides `[patch.crates-io]` path/git pins (patches do not propagate to dependents, so a published crate would be unbuildable), and the binary's distribution channel was never crates.io anyway. The release identity is the `release-binaries.yaml` archive workflow — platform archives named `specify-<target>.tar.gz` attached to the GitHub release, which `specify upgrade` and the install scripts already consume. `docs/release.md` documents this as the only binary channel.

- **No crate-name/`[[bin]]` collision.** The root package `specify` owns the one `[[bin]] specify`; the `specify-runtime` crate is a library whose only binary target is the differently-named `specify-runtime-replay` (dev/test surface, never released). Nothing ships a second `specify`.
- **Re-pin before merge.** The `[patch.crates-io]` sibling-path pins (omnia crates, `omnia-cursor`) must move to pushed git revs before the migration PR merges — that restores reproducible CI/release builds but does not restore crates.io publishability (git deps are equally unpublishable); `publish = false` stays until the omnia crates are published and the patches drop.

## Old-stack deletion (milestone S4)

**Decision (2026-07).** The envelope machinery and its native handlers are deleted; the triage predicate (`guest::owned`) widens to the full parity-matrix guest-owned set. The final split: **guest-routed** — `plan execute`, `plan author`, `slice refine`, `slice build`, `slice merge run`, `source survey`, `source extract`; **native** — everything else, including the guest-owned-but-pure in-process verbs (`plan create/add/amend/next/status/transition/validate/archive`, `slice create/validate/transition/provenance/model show/merge preview/merge conflict-check/touched-specs/task`, `source resolve`, `target resolve`, `journal emit/show`) and the host-machine residue (`init`, `upgrade`, `plugins`, `lint`, `workspace`, `registry`, `adapter`, `rules`, `archive`, `contract`, `completions`). **Amendment (RFC-65 moves 1 + 5):** this S4 split is itself superseded — the pure verbs, `registry`, `rules export`, `archive prune`, `completions`, and init's scaffold leg all moved guest-side, the native set shrank to the closed provisioning verbs plus the acknowledged `workspace` residue, and `guest::owned` and every native workflow-verb handler are deleted; see [§"The provisioning front (RFC-65 move 5, amending D-bin)"](#the-provisioning-front-rfc-65-move-5-amending-d-bin). What died with the cut:

- **Envelope machinery.** `--phase prepare|finalize` on `source survey` / `source extract` / `slice build`, the `--dry-run` / `--from` pairs on `slice synthesize` and `plan propose`, the native two-phase `slice build` handler with its `prepare.argv` hook dispatch (vectis asset materialization is an in-guest build prelude now), and the shared source prep seam (`src/runtime/commands/source/{op,prep}.rs`). The synthesis and propose kernels survive in `specify-workflow` — the guest orchestrators (`orchestrate::{refine,author}`) are their only callers.
- **`extension run/fetch/gc/schema` (whole verb family).** The vectis and contracts tools are in-guest adapter library code; nothing host-side dispatches an adapter WASI tool anymore. `specify-registry` **shrinks, not dies**: `pack` / `oci` / `store` (used by `adapter build/publish` and `init`) plus the `lint project` WASI path — `host::{RunContext, WasiRunner}`, `resolver::resolve` with its fetch-on-miss cache, `permissions` — survive for project-scope `tools[]`; the adapter-scope extension declarations, the `gc` scan, and the plugin-tool merge are deleted. The manifest-DTO leaf `specify-extension` survives as the `tools[]` shape.
- **D-catalog-infer: `catalog infer` dies with the old stack.** Both halves — the `report` phase's cluster judgment and the `bind` phase's deterministic fingerprint→slug bookkeeping — live in the in-guest vectis core (adapters commit `3cb9c36`), driven by the build's own artifacts (`${SLICE_DIR}/build/component-bindings.yaml`), not a manifest capability field. No native verb survives, and nothing engine-side may hardcode "vectis is catalog-capable" — the RFC invariant that no adapter name enters the `specify:adapter` contract holds. The operator-curated catalog (§"Component catalog") and `slice-catalog-drift` validation are unchanged.
- **D-planlock: `plan lock -- <cmd>` retired; `require_held` gates unwound.** The flock fenced separate OS processes racing one plan through the native breakout loop; with the breakout verbs guest-routed there is no multi-process native driver left to fence. The D1 guest marker (`.specify/guest.lock`, `guest-marker-held`) is the only concurrency fence; the D3 workspace refusal stays. `plan next` / per-entry `transition` / the merge `done` stamp run lock-free natively — single-writer discipline is the operator's, exactly as it is for hand-edited artifacts.
- **D-preview: `source preview` retired.** It was the last consumer of the shared prep seam, and its purpose — a workflow-free dry-run of the extract sandbox — describes machinery that no longer exists. A future debugging surface, if earned, is an in-guest concern.
- **D-workspace: workspace-mode regression, documented not fixed.** `--plan-dir` is native-only, and the guest anchors plan artifacts at the `"."` preopen — so workspace-routed plans (plan at the workspace root, phases in a slot) cannot drive the guest-routed phase verbs. `plan author` / `plan execute` already refuse workspace plans (D3); the S4 cut extends the same gap to breakout `slice build` / `slice merge run` / `source survey|extract` in slots. Workspace routing regains the loop when slot routing has an in-guest counterpart (its own RFC); until then workspace plans are authored and driven by hand with the native pure verbs.
- **Manifest schemas close.** The S2 two-shape window ends: `briefs`, `execution`, `extension`, `prepare`, `host_prereq`, `finalize_verify`, and `catalog` are deleted from `schemas/{adapter,source,target}.schema.json` and the resolver structs; only the post-cutover shape (`name`, `version`, `axis`, `description`, target `inputs`/`platforms`/`specify`) validates, and retired keys are rejected at load time by `additionalProperties: false`. `operations()` returns the axis's closed WIT operation set. `ADAPTER_WASM_FILENAME` (the extension component) gives way to `ADAPTER_GUEST_FILENAME` (`guest.wasm`).
- **Finalize-era checks die with the finalize path.** `evaluate_ui_surface_coherence` and helpers left `slice/build/wire.rs` (ported to the vectis core); `BuildOutcome` drops its `warnings`. `wire.rs` keeps the `BuildRequest` / `BuildReport` DTOs, their schema gates, and `enforce_report_slice` / `enforce_report_success` — the guest's `orchestrate::build` finalize tail consumes them.
- **Wire codes and tests.** Thirty retired discriminants left `WIRE_CODES` (the `plan-lock-*`, `plan-propose-*` mode/envelope, `slice-synthesize-*` mode/envelope, `source-*` prep, `catalog-*` infer, `target-build-*` hook, and extension-cache families). The journal taxonomy is untouched — every event id retains an emitter (guest-side orchestrators or `journal emit`). The native two-phase integration suites were deleted rather than ported: the behavior they pinned is covered by the workflow-crate orchestrator tests and the composed guest tests, and the triage routing for the widened set is pinned in `tests/guest.rs`.

## Deterministic guest merge (RFC-61 Step 4, decision D2)

**Decision (2026-07).** The guest merge (`orchestrate::merge`, behind `specify slice merge run` and the execute loop's merge leg) is **deterministic-only**: the `TargetSeam` trait carries `guidance` + `build` and deliberately omits the WIT contract's `merge` operation, so no target merge brief is ever dispatched from the guest. Consequences:

- The delta merge, Decision Record promotion, `merged` transition, archive move, outcome-ledger append, and per-entry `done` stamp are the same native code (`merge::slice::commit`) driven in-guest; the `slice.merge.started` / `.succeeded` / `.failed` bracket is unchanged.
- The native workspace-clone git commit leg is skipped with an explicit `slice.merge.commit-skipped` journal event — the guest owns no git surface, and lifecycle authority is `.specify/` state, so `done` still stamps. The durable `slice.archive.created` ledger entry lands with `merge-sha` absent; a journal reader can tell a guest merge from a native one by exactly these two signals.
- The brief-driven verification legs (pre-merge target gates, the contracts post-merge validator) do not run under guest merge. Verification moves agent-side into target prompts at Step 5 (the `verify` grant stays stubbed per the deferred verify-profiles RFC); the cutover review confirms each first-party target's prompts carry the checks before the native path is deleted.
- The WIT `merge` operation stays in the contract as the forward hook for a judgment-backed merge (conflict resolution behind the model); adding a seam method later is additive.

## Workflow judgment prose is pasted, not shelved (RFC-61 Step 4, decision D8)

**Decision (2026-07).** The workflow guest's prompt corpus — the propose and synthesize prompt bodies plus the synthesis playbook references (`plugins/spec/references/synthesis/*`, `spec-format.md`) — is embedded via `include_str!` (`crates/workflow/src/judgment/prose.rs`) and **pasted into the system prompt**, not served over MCP references. The corpus is about 50 KB and every section is load-bearing on every synthesis call, so lazy fetching buys nothing and an MCP route on the workflow guest would exist only for this. The adapters keep the opposite posture (MCP references up to 700 KB, fetched lazily by the spawned agent) — D8 is a size-and-locality call, not a new architecture. Markdown stays the authoring source of truth; the dependency direction forbids importing the adapters' `specify-prose-registry`, so the crate embeds the repository files directly.

**Decision (2026-07).** RFC-61 requires a `Model` capability in `omnia-guest::capabilities` (WASI-backed default body on `wasm32`, bare signature off it); it has not landed upstream yet. Rather than block Step 4, the engine carries `specify-guest-model` — a leaf crate holding the `Model` trait (request/reply DTOs, `create`), the `wasm32` default body over the `omnia-wasi-model` bindings, and `MockModel` off `wasm32` — as the **documented stand-in**. Standing constraints:

- New-crate justification (per §"New workspace crates"): the trait cannot live in `specify-workflow` because the `wasm32` default body needs the `omnia-wasi-model` dependency, which must stay out of the workflow crate's native compile graph; a leaf keeps the edge one-directional (`workflow → guest-model`) and lets adapters-side code share the identical shape.

## `specify-dispatch`: the wasm-clean dispatch boundary (RFC-61 Step 4, Milestone D)

**Decision (2026-07).** The CLI grammar, output envelopes, exit-code contract, project `Ctx`, and every pure workflow verb handler moved from the root binary into the wasm-clean `specify-dispatch` crate, consumed by both the native binary and the workflow guest shim. Standing choices:

- **One grammar, two dispatchers.** The full clap tree — native-only verbs included — parses identically everywhere, so `--help`, completions, and usage-error exits are byte-compatible. The native dispatcher keeps the residue handlers in the binary crate; the guest's `guest::route` three-way split runs pure verbs in-process, returns the four collapsed orchestrator verbs (`source survey`, `source extract`, `slice build`, `slice merge run`) plus `plan execute` as an `Orchestration` descriptor, and refuses residue verbs.
- **The sync/async seam sits at the shim.** `specify-dispatch` is fully synchronous and WIT-free (no wit-bindgen, wasip3, wasmtime, or `specify-registry` in its graph); the `workflow-guest` shim owns the async surface — the WIT bindings async-lower because the seam operations await the async `omnia:model` import mid-call, and `verbs::drive` is the only async driver. Orchestration verbs are *parsed* in the dispatch crate but *dispatched* in the shim, where the `Model + SourceSeam + TargetSeam` provider lives. This keeps the dispatch crate natively testable with no executor and keeps every wasm specific in the shim, per the RFC's crate-architecture invariant.
- **New-crate justification (per §"New workspace crates"):** the handlers could not stay in the root binary (the guest cannot depend on a bin crate, and the binary's graph carries wasmtime via `specify-registry`), and they could not move into `specify-workflow` (which is deliberately clap-free). The crate enforces the `workflow → dispatch → {binary, guest-shim}` direction; without it either the guest would link wasmtime or workflow would grow a clap dependency.

## Source and target adapter role names

The output-role domain types are spelled `Target*` (`Target`, `Slice.target`, the `slice-create-target-missing` / `init-requires-adapter-or-workspace` discriminants, plus every fixture, JSON envelope, and call site). The shared manifest *shape* is loaded by the axis-aware module `crates/workflow/src/adapter/` (`SourceAdapter` / `TargetAdapter` / `Axis` / `ResolvedAdapter` / `AdapterLocation`). Briefs are resolved by path through `briefs.<op>`; they carry no YAML frontmatter and the CLI never reads their bodies. The slice-metadata wire uses `Operation { Shape, Build, Merge }` (`phase: shape | build | merge`).

Per workflow §"Note to the implementing agent", touching any of these symbols requires an `rg` sweep across both the Rust workspace and the surrounding `augentic/specify` prose in the same PR.

## Adapter loader axis routing

`SourceAdapter::resolve` / `TargetAdapter::resolve` probe the out-of-tree manifest cache (`<project-cache>/manifests/{sources,targets}/<name>/`) then the in-repo tree (`adapters/{sources,targets}/<name>/`) — order and layout pinned in [workflow.md §"Resolver and cache"](./docs/standards/workflow.md#resolver-and-cache). The decisions:

- **Resolution is project-local, plus the global package store.** There is no environment-variable fallback to an out-of-tree framework checkout. A project carries a manifest-cache mirror or a vendored `adapters/` tree, or lets the first-party shorthand fetch at `init` time; RFC-48 D5 adds one non-project source — the global content-addressed adapter store, probed **first** for a pinned `(name, version)` package ref (see [§"RFC-48 adapter store and transport"](#rfc-48-adapter-store-and-transport)). A miss on every probe is `adapter-not-found`.
- **The axis segment is load-bearing.** `sources` / `targets` keeps colliding names disambiguated by axis; cache placement matches the probe layout (`cache_dir(axis, name)`). See [§"Cache layout"](#cache-layout).

### First-party `<adapter>` shorthand at init

`specify init <adapter>` accepts a first-party **shorthand** — `^[a-z][a-z0-9-]*(@<semver>)?$` (`omnia`, `omnia@1.0.0`) — alongside the local-path and GitHub-URL forms. A bare name carries no version pin (resolves the single installed identity); a `name@<semver>` pin records the full `name@<semver>` identity on `project.yaml.adapter` (RFC-47). `AdapterUri::parse` (`crates/workflow/src/init/adapter_uri.rs`) expands the shorthand to the canonical published adapter `https://github.com/augentic/specify/adapters/targets/<name>@<git-ref>`, deriving the **git checkout ref `v<major>`** from the pinned semver. RFC-48 has since landed, but the first-party shorthand stays git-based (H3) — only the `specify:<name>@<semver>` package-ref form pulls from the OCI store (see [§"RFC-48 adapter store and transport"](#rfc-48-adapter-store-and-transport)). `init` is target-only, so the shorthand resolves under `adapters/targets/`; anything carrying `:` or `/` (including a `@v<major>` git-ref form) is not semver shorthand and continues through `from_local` / `from_github` unchanged.

### Adapter identity: semver version + `AdapterRef` (RFC-47)

`adapter.yaml.version` is a **required semver string** (`x.y.z` with optional `-prerelease` / `+build`), enforced by the per-axis JSON Schema and parsed into `SourceAdapter.version` / `TargetAdapter.version` as a typed `semver::Version`. It is the adapter's **identity**, not a descriptive field: synthesized target refs (`topology.lock`, proposal, slice metadata, build-report) render `name@<semver>`, and `TargetRef::parse` requires the `name@<semver>` form (the legacy `name@v<major>` is no longer a valid target).

The loader threads identity through a value type — `AdapterRef { name: String, version: Option<semver::Version> }` (`crates/workflow/src/adapter/core.rs`). `SourceAdapter::resolve` / `TargetAdapter::resolve` take `&AdapterRef`; `locate_axis` stays name-only for the probe (project-local single-identity world). Two gates back the identity:

- **`adapter-version-malformed`** — the post-schema load gate (`check_version`) rejects a manifest whose raw `version` is absent or not exact semver, before typed deserialization, so the diagnostic names the field rather than surfacing a generic parse error.
- **`adapter-version-required`** — `check_requested_version` rejects a pin (`AdapterRef.version = Some(_)`) that does not match the installed manifest identity. Latent in the single-identity world (a `None` pin always picks the installed identity); wired now so RFC-48's multi-identity store widens the same seam.
- **`adapter-cli-too-old`** — RFC-47 D3 host-CLI compatibility floor. `adapter.yaml` carries an optional `specify` semver string (parsed into `requires_specify: Option<semver::Version>`); the post-schema gate `check_requires_specify` compares it against the running binary (`env!("CARGO_PKG_VERSION")`) and aborts with `Error::AdapterCliTooOld` on the exit-3 `EXIT_VERSION_TOO_OLD` path when the binary is older — the adapter-granularity analog of the `project.yaml.specify` floor. Exact floor only (no ranges, matching the version-pin posture); absent means no floor. The check is transport-independent (identical for `Local`, `Cached`, and any future registry tree).

A `sources.<key>.version` optional pin on `SourceBinding` (and `sourceBinding` in `plan.schema.json`) carries the same `Option<semver::Version>` — additive, so existing `plan.yaml` binds parse unchanged.

**Transport: RFC-47 baseline, RFC-48 has since landed.** RFC-47 itself changed no transport — the first-party shorthand still derives the git checkout ref `v<major>` from the pinned semver and distributes as a git sparse checkout of `augentic/specify` (H3 keeps the shorthand git-based). RFC-48 then landed the packaging/transport layer RFC-47 had deferred: single-layer OCI packaging and a global content-addressed `(name, version)` store backing `specify:<name>@<semver>` package refs (see [§"RFC-48 adapter store and transport"](#rfc-48-adapter-store-and-transport)). Third-party namespacing beyond the `specify:` namespace, a per-adapter release index, a semver-*range* `specify`-floor policy, and a cross-version compatibility matrix stay deferred to RM-21.

## RFC-48 adapter store and transport

RFC-48 lands adapter packaging and transport on top of the RFC-47 identity. Implementation lives in `specify-registry` (`crates/registry/src/{pack,oci,store,host}.rs`). The deliberate decisions — including the deviations from the RFC's stated defaults:

- **Single-layer OCI packaging (O1).** An adapter publishes as **one** packed `tar+zstd` layer carrying prose and the built `adapter.wasm` together, not the RFC's two-layer prose+wasm default. The Step-1 spike showed `wasm-pkg-client` / `wkg` reject an opaque (non-component) blob in both directions, so a multi-layer opaque artifact bought nothing and one content-addressed layer is simpler. Consequence: an extension-only rebuild re-pushes the whole layer (there is no per-file delta).
- **Blocking install lock (O3).** `store::install_layer` serialises concurrent installers of one identity behind a sibling lock taken with a **blocking** `File::lock()` (wait), not the `File::try_lock` family the `/spec:execute` driver lock uses. For an install, waiting for the peer to finish materialising the immutable entry is preferable to failing fast; the post-lock re-check makes the loser a no-op.
- **Separate `AdapterLocation::Store` variant (D5).** Store-sourced adapters get their own `AdapterLocation::Store` arm rather than reusing `Cached`. `locate_axis` probes the store **first** for a pinned `(name, version)` (ahead of the manifest cache and the vendored tree), so a pin always prefers the immutable store entry.
- **D4 verify-on-read is wired (H2).** `install_tofu` records a deterministic tree content digest of the unpacked store entry into a sibling `<store>/<name>@<version>.meta`; resolve recomputes the digest and verifies it for `AdapterLocation::Store` entries only — raising `adapter-digest-mismatch` — leaving `Local` / `Cached` exempt. A store entry with no recorded `.meta` sidecar **fails open**: verify-on-read rejects a recorded-then-drifted digest, never an absent record (so a pre-D4 entry resolves unchanged). The registry layer digest stays the publish-time anchor (verified on the publish pull-back); under single-layer OCI, read-time verification uses the cheaper tree content digest rather than re-tarring the entry.
- **First-party shorthand stays git-based (H3).** `specify init <name>@<ver>` still resolves through a git sparse checkout plus the per-project manifest cache; only the `specify:<name>@<semver>` package-ref form pulls from the OCI store. Routing the shorthand through the store would need a version-resolution step (RM-21) and is deferred.
- **Resolve-in-place for store entries (L3).** Store-sourced adapters skip the per-project manifest-cache copy — the read-only, content-addressed store entry is resolved in place rather than mirrored into `<project-cache>/manifests/`.

## One component, no manifest (Milestone R64-S)

RFC-64 (RFC-61 Step 5, Milestone R64-S) collapses the adapter artifact to a single WebAssembly component: `adapter.yaml`, the per-axis manifest JSON Schemas, the manifest cache, the packed prose tree, and the committed per-adapter `guest.wasm` are all gone. Identity is the published package (`augentic:<name>@<semver>`); metadata is the component's own `describe` answer. This supersedes the manifest halves of §"Adapter loader axis routing", §"Adapter identity: semver version + `AdapterRef`", §"RFC-48 adapter store and transport" (packaging and probe-layout bullets), §"Adapter manifest requireds", §"Adapter name uniqueness", and the adapter-guest-discovery bullet of §"One `specify` binary" (the `<resolved-dir>/guest.wasm` tree probe — the guest leg now resolves single components) — those entries stay as history. **Amendment (RFC-65):** the naming cut renames every first-party package identity `augentic:<name>@<semver>` → `specify:<name>@<semver>` (`specify:core` becomes the core guest's registry identity); the `augentic:` namespace is reserved for future org-wide contracts and carries no first-party routing. The `augentic:` identities below are the pre-cut spelling; the registry host stays `augentic.io`. Pre-1.0 hard cut: no aliases — pinned projects re-init. The R64-S decisions:

- **Describe-driven resolve with a resolve-time cache.** An adapter's non-identity metadata (`specify-floor`, a target's `inputs[]` and `platforms`) comes from the deterministic `describe` export on its axis interface (a plain WIT `func` — deterministic metadata cannot fail, so no `result` wrapper and no async lift). Dispatch is host-side, instance-per-call, at resolve time: `specify-workflow` stays wasmtime-free behind a process-global `DescribeRunner` function-pointer seam (`adapter/describe.rs`) that the root binary registers at startup (`src/runtime/commands/describe.rs`, backed by `specify_runtime::describe`). The answer persists as a `<component>.describe.json` sidecar keyed by the component file's SHA-256, so a store entry is described once per install and a development build once per rebuild. An unregistered runner (e.g. inside the workflow guest, which never resolves adapters) is the typed `adapter-describe-unavailable`. The describe instance links *every* import — WASI included — as a trap (`describe` is effect-free by contract), with linker shadowing enabled because a wasip2 guest imports the same WASI interface at two versions (std's 0.2.0 beside wit-bindgen's newer 0.2.x) and the semver alias keys collide otherwise.
- **Axis by export introspection, mismatch typed at resolve.** The store carries no axis segment (entries are keyed `name@version` alone) and there is no manifest `axis` field. Where an unbound component must be classified — the guest-leg scan over the project component cache — `specify_runtime::describe::sniff_axis` does one cheap `wasmparser` pass over the top-level component export names (no compile). Where a binding names the axis — every `SourceAdapter::resolve` / `TargetAdapter::resolve` — the describe dispatch checks the component's exports before instantiating and raises the typed `adapter-axis-mismatch` (naming the expected and found interfaces) when the component implements the other axis. `adapter-name-axis-collision` retires with the axis-split trees.
- **wasm-pkg transport over a single-file store.** `pack_adapter` and the raw-OCI tree layer are retired; publish is `wkg publish` in the adapters repo and pull is `wasm-pkg-client` (`registry::package`) against the `augentic:<name>@<semver>` package identity. The store entry is one file — `<store-root>/<name>@<version>.wasm` — with the component-byte SHA-256 recorded in the sibling `<name>@<version>.meta`; RFC-48's verify-on-read (fail-open on an absent record), blocking install lock, atomic temp-then-rename, and `.specify/adapters.lock` semantics carry over unchanged onto the one file. **Amendment (RFC-65):** the store root resolves `$SPECIFY_ADAPTER_STORE` (absolute override — the relocation lever for sandboxes and tests), else `$HOME/.specify/adapters` — an install store in Specify's per-user home, not an evictable OS cache, so the XDG legs are gone with no compatibility fallback; the per-project derived cache under `$XDG_CACHE_HOME/specify/projects/` is unaffected.
- **Committed-artifact retirement.** No adapter tree commits a built `guest.wasm`. Development resolution probes the release build `target/wasm32-wasip2/release/<name>.wasm` under the project itself, then under the sibling `specify-adapters` checkout — built once via `cargo make release` in the adapters repo (the repo-root `omnia.toml` points at the same sibling paths). A development component carries no package identity and resolves as the honest `0.0.0` placeholder (`dev_version()`) in topology projections and envelopes.
- **Init posture.** `specify init` accepts three adapter forms: a local `.wasm` path (mirrored into the project component cache at `<project-cache>/components/<name>.wasm`, name from the file stem), a package reference (`augentic:<name>@<semver>`, TOFU-installed into the global store before scaffolding), and the versioned first-party shorthand (`omnia@1.0.0` — sugar for the package reference). The GitHub sparse checkout no longer yields a usable artifact, so GitHub URLs are refused with the typed `adapter-github-uri-unsupported`, and a bare first-party name (`omnia`) is the development shorthand — it requires the sibling release build and errors honestly (`adapter-not-found`, naming every probed path and the `cargo make release` / pin remedies) instead of silently fetching a tree that cannot resolve.

## Plan lifecycle: two stored states

`plan.yaml.lifecycle` is `pending | approved` — no plan-level `in-progress` or `drained` ships in v1; "drained" is computed at read time as "every entry is `done`", not stored. Per-entry status is the closed `pending | in-progress | done` with split writer ownership (see [§"Lifecycle write-ownership"](#lifecycle-write-ownership)). `specify plan transition <plan-name> approved` is Gate 1 and operator-only: the CLI deliberately does not gate it (operators run it from any shell), the `--help` text documents the rule, and `/spec:plan` skill bodies MUST NOT call it.

Per-entry status walks backwards only via `specify plan transition <entry> --undo`, which refuses to skip rungs — exactly `Done → InProgress` and `InProgress → Pending` per call, one `plan.transition.undone` journal event per rung. `Status::Reopened` does not exist: an undone `done` row walks back to `in-progress` so the operator can re-run `/spec:build` and re-merge without a new state. If an upstream revert demands a redo without re-running the slice, author a fresh slice; the original `done` row stays as the historical record. Plan-level lifecycle has no undo path in v1.

Archive is a filesystem operation, not a lifecycle state: `specify plan archive` moves `change.md` + `plan.yaml` into `.specify/archive/plans/`, and the lifecycle stamp inside the archived file stays `approved`. There is no `archived` enum variant — the on-disk location is the signal.

## `SliceSourceBinding`: bare shorthand plus structured form

`plan.yaml.slices[].sources` is one in-memory struct (`{ source_key, lead_id: Option }`) with a custom `Deserialize` accepting two wire shapes and a `Serialize` emitting whichever shape produced the value: the bare string `legacy` (lead falls back to the owning slice's name via `lead_id(slice_name)` — the one-source-per-slice degenerate case, predominantly `intent`), and the structured `{ source, lead }` (required whenever key and lead differ).

Collapsing the variants into one struct means every consumer goes through the same `source_key()` / `lead_id()` accessors instead of `match`-ing a discriminator — the shorthand stays a pure parser concern. Construct in tests via `SliceSourceBinding::bare(..)` / `::structured(..)`. Refer to workflow §"Source".

## `Divergence` enum

`plan.yaml.slices[].divergence` is the closed enum `none | likely | accepted | rejected` (kebab-case wire; `none` is the elided default). `specify plan amend --divergence` only accepts `accepted | rejected` — `likely` is reserved for the `propose` sub-step of `/spec:plan`. Operators flipping the field after Gate 1 use `accepted | rejected` exclusively. Refer to workflow §"Plan-time reconciliation".

RFC-46 D4 adds the sibling `plan.yaml.slices[].disagreements[]` (`{ field, values: [{ source, value }] }`, the `Disagreement` / `DisagreementValue` types), authored by the propose agent alongside a `divergence` flag and carried from the proposal `responseSlice` onto the plan entry by the reconcile kernel. The CLI never decides materiality; `Plan::validate` only checks structural consistency and surfaces it as **advisory** (`Suggestion`) findings: `slice-divergence-unrecorded` (a live `likely`/`accepted` flag without ≥2 distinct source values per recorded field) and `slice-divergence-orphan-values` (recorded values with no flag). Both are deliberately non-blocking — `divergence` is operator-settable standalone via `plan amend --divergence` (advisory metadata in v1), so a divergence-consistency finding may never break that contract-locked write; it surfaces at `plan validate` / Gate 1 instead.

## Plan per-slice authority overrides

`plan.yaml.slices[]` carries an optional `authority-override` map keyed by claim kind, valued by source key. Keys come from the closed claim-kind enum; values MUST be source keys present in the slice's own `sources[]` list — orphans are rejected by `specify slice validate` (`slice-authority-override-orphan-source`). The map is scoped to one slice; plan-wide and project-wide overrides are out of scope.

## Extraction is agent-only — no cache, no fingerprints

Source extraction supports exactly one execution mode: `agent`. The deterministic-extraction substrate that once sat behind it — the extraction cache at `.specify/cache/extractions/<adapter>/`, the closed five-input `CacheFingerprint`, the `cache: opt-out` manifest field, the `source.survey.cache-hit/-miss` and `slice.extract.cache-hit/-miss` journal events with their `CacheMissReason` enum, the `Flow::dispatch_tool` seam in the source op kernel, and `specify source resolve --explain` — was deleted per YAGNI. Agent outputs are non-deterministic, so no run was ever served from the cache; the machinery only constrained changes to the live agent path. `source.schema.json` now enumerates `execution: ["agent"]` for sources (targets keep `agent | tool` — the target-side WASI build dispatch is real). The finalize phases emit plain completion events (`source.survey.completed` / `slice.extract.completed`) instead of cache-probe outcomes. If a deterministic source ever lands, re-add caching behind a fresh decision — the journal taxonomy and manifest schema are the seams to widen.

### `specify journal emit` — guarded front door (D12)

Deterministic commands emit their own events. Agent-orchestrated phases that have no deterministic emit command write through `specify journal emit <event-id> [--payload <json>] [--format json]`. The verb mints **no event kinds of its own** — it is a guarded front door onto the same closed `EventKind` taxonomy, preserving "one closed taxonomy, one writer". The closed enum is itself the per-kind payload schema (no parallel JSON-schema registry): the handler reassembles the adjacently-tagged `{ event, payload }` shape and deserialises it into `EventKind`. An unknown tag fails `journal-emit-unknown-event`; a missing required field fails `journal-emit-payload-schema` (both exit 2). The CLI — never the agent — stamps the UTC `timestamp` and appends exactly one line.

## `$CAPABILITY_DIR` replaces `$ADAPTER_DIR`

The WASI tool runner's plugin-scope substitution variable is `$CAPABILITY_DIR`. It expands to the resolved adapter's root directory (historically the out-of-tree `<project-cache>/manifests/{sources,targets}/<name>/`, retired with the manifest mirror — see [§"One component, no manifest (Milestone R64-S)"](#one-component-no-manifest-milestone-r64-s)) and is only valid in `permissions.{read,write}` entries; project-scope references are rejected as `tool.capability-dir-out-of-scope`. The token survives in the `specify-extension` validation surface for the project-scope `tools[]` shape; with adapter-scope tool declarations deleted and `lint project` retired, no live dispatch path expands it today.

## Lifecycle write-ownership

Per-entry status writes route to exactly one CLI verb. Skill bodies never write status by hand; the CLI is the single source of truth for each transition:

| State                     | Writer                                    | Trigger                                                                                                                                                    |
| ------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending` (per-entry)     | `specify plan add` / `specify plan amend` | Operator (or `/spec:plan`) authors / edits a slice row.                                                                                                    |
| `in-progress` (per-entry) | `specify plan next`                       | Sole writer; the `/spec:execute` loop calls it once per slice.                                                                                             |
| `done` (per-entry)        | `specify plan transition <entry> done`    | Called by `/spec:merge` after `specify slice merge` succeeds.                                                                                              |
| `pending` (plan-level)    | `specify plan create`                     | `/spec:plan` scaffolds the plan in `pending`.                                                                                                              |
| `approved` (plan-level)   | `specify plan transition <plan> approved` | Operator-only (Gate 1). The CLI is ungated; `/spec:plan` MUST NOT call this verb — `--help` text documents the rule and the skill body is the actual gate. |

The plan-level `approved` row is the lightest-touch shape the workflow allows: a wholly operator-driven stamp with no CLI-side authentication. Skills that drift from this contract get caught at review time. Refer to workflow §"CLI surface" and §"Writer ownership".

## Plan source bindings

The on-disk shape of `plan.yaml.sources.<key>` is the structured `{ adapter, path?, value? }` object — the 1.x bare-string shorthand was dropped at the Specify 2.0 cut. Every binding carries an explicit kebab-case `adapter` and exactly one of `path` / `value`, enforced in both the JSON Schema and the Rust loader. The `specify plan create --source` flag grammar mirrors the wire shape:

| Form                                       | Materialises as                                                 |
| ------------------------------------------ | --------------------------------------------------------------- |
| `--source <key>=<adapter>:<path>`          | `SourceBinding { adapter, path: Some(<path>), value: None }`    |
| `--source <key>=<adapter>:value:<literal>` | `SourceBinding { adapter, path: None, value: Some(<literal>) }` |

The adapter is the substring up to the first `:` after `=`; the binding payload is everything after it, so URLs containing `:` round-trip through the path form unchanged, and the `value:` sentinel switches the parser to literal mode (the literal may contain any character without escaping). No shorthand exists for "the adapter name equals the key". Source keys are plan-scoped; each key maps to exactly one binding, but slices may reference the same key with different leads.

## Adapter manifest requireds

`description` is required at the top level of every adapter manifest — sources and targets alike — alongside `name`, `version`, and `axis` (`adapter.schema.json` `required: [name, version, axis, description]`). The schemas are closed (`additionalProperties: false`) around the post-cutover shape: the only optional keys are `specify` (minimum CLI version) plus the target-only `inputs` and `platforms` — the retired handoff keys (`briefs`, `execution`, `extension`, `prepare`, `host_prereq`, `finalize_verify`, `catalog`) are rejected at load time (see §"Old-stack deletion"). Adapter manifests carry no extension declaration; project-scope `tools[]` (in `.specify/project.yaml`, validated by `extension.schema.json`) keep requiring `name`, a strict-semver `version`, and `source` per entry. Top-level adapter requireds are enforced uniformly by all three adapter schemas.

## Adapter name uniqueness

Adapter names are unique across axes — a name is declared under `adapters/sources/<name>/` xor `adapters/targets/<name>/`, never both (likewise their manifest-cache mirrors). Eagerly enforced at `specify init` (`init/cache.rs::cache_adapter`) and at every `*Adapter::resolve` (`adapter/core.rs::locate_axis` probes the opposite axis for a sibling manifest; `specify` is fork-and-exit, so two `is_file` probes beat memoised process-global state). Collisions surface as `adapter-name-axis-collision`, naming both axes so operators can rename or delete one side without grepping the tree.

## Target platform capability and init validation

Target adapters may declare an optional `platforms` capability (`{ required: bool, allowed: [Platform], default: [Platform] }`) in their manifest. `PlatformsCapability` lives on `TargetAdapter` in `crates/workflow/src/adapter/core.rs`; the schema shape is in `target.schema.json`. When `required` is true, `specrun init` demands `--platforms <csv>` and enforces three validation rules (all exit 2): `project-platforms-required` (target requires platforms but flag absent), `project-platforms-must-include-core` (`core` missing from the set), and `project-platforms-not-allowed` (a token outside `allowed`). The same three rules re-fire as backstops at `TopologyProject::resolve` (`topology-cache-project-platforms-*`). The mutation path is `specrun init --upgrade --platforms <csv>` — `--platforms` is deliberately excluded from the `--upgrade` conflict set. The `Platform` enum (`Core | Ios | Android | Web | Desktop`, kebab on the wire) lives in `crates/workflow/src/platform.rs`.

`platforms` rides the same topology projection rails as `target`: `TopologyProject` and `topology-lock.schema.json` carry it, `workspace sync` re-projects it, and the propose `projectRef` envelope carries it so downstream phases see the declared set. Greenfield `scaffold_greenfield` injects the manifest's `default` when the target declares `platforms.required`.

Platform shell bootstrap is **not** a CLI concern. The reconcile kernel performs no filesystem detection and inserts no bootstrap slices: `project.yaml.platforms` is the sole authority for platform intent, and standing up an absent shell tree is the bound **target adapter's** build-time responsibility — the vectis adapter owns its Crux shell scaffolding (and any launcher-icon gating) in `augentic/specify-adapters`, mirroring how the omnia target stands up its own surface. The CLI itself performs no shell detection, inserts no bootstrap slices, and runs no launcher-icon gate.

## Cache layout

`.specify/` is **Specify's directory: committed config plus system-of-record** (`project.yaml`, `specs/`, `slices/`, `archive/`, `journal.jsonl`, the lock sidecars). Its lone gitignored in-tree tenant is **`.specify/scratch/`** — transient working state: per-run lanes recreated empty by their owning verb, deletable at any time at zero cost. Everything regenerable and machine-owned now lives *outside* the working tree:

- **The cache is out-of-tree.** The adapter manifest mirror and the distributed codex live in a per-project directory inside the user's OS cache (`$SPECIFY_PROJECT_CACHE`, else `$XDG_CACHE_HOME/specify/projects/<project-id>/`, else `~/.cache/...`), keyed by a stable digest of the canonicalised project path (see [`crates/schema/src/cache.rs`](./crates/schema/src/cache.rs)). Each checkout — including each materialised workspace slot — gets its own collision-free cache that survives `git clean` and never pollutes the working tree.
- **Workspace slots are top-level.** Materialised registry peers live at `<project>/workspace/<peer>/`, not under `.specify/`. Remote peers are `git worktree`s of a persistent out-of-tree bare mirror (`$SPECIFY_MIRROR_CACHE`, else `$XDG_CACHE_HOME/specify/mirrors/<url-id>.git`), so a peer's object store is shared across changes and fresh checkouts; local peers stay symlinks.

`ensure_gitignore_entries` therefore writes exactly two entries — `.specify/scratch/` and the top-level `workspace/`. There is no in-tree `.specify/cache/` to ignore.

The out-of-tree per-project cache hosts two root-disjoint tenants, each self-describing via a provenance stamp so the cache root holds only directories:

- `manifests/{sources,targets}/<name>/` — the adapter manifest mirror (per-axis because adapter names are unique per axis), with provenance at `manifests/manifest-meta.yaml`.
- `codex/` — the distributed shared-rules codex, with provenance at `codex/codex-meta.yaml`. See [§"Shared codex distribution"](#shared-codex-distribution).

**Amendment (RFC-64/RFC-65):** the manifest mirror retired with the one-component artifact (see [§"One component, no manifest (Milestone R64-S)"](#one-component-no-manifest-milestone-r64-s)). The per-project cache's tenants today are `components/` (operator-supplied local `.wasm` components mirrored at init), `deployment/` (the generated deployment manifest, `omnia.toml`), and `codex/` (unchanged). The out-of-tree root, keying, and gitignore posture above are unchanged.

There is no extraction-result cache — see [§"Extraction is agent-only — no cache, no fingerprints"](#extraction-is-agent-only--no-cache-no-fingerprints). A manifest-cache directory is therefore always a manifest mirror; the loader never probes for co-tenancy.

`.specify/scratch/` hosts the per-run lanes (`<adapter>/{survey,<slice>}/`, `plan/`), each recreated empty by its owning verb so a stale artifact from a prior run can never be consumed as this run's output. Scratch stays rooted inside `.specify/scratch/`, structurally disjoint from the out-of-tree cache, so a scratch write can never pollute a cache artifact.

## Target adapter suffix policy

A plan slice does not store its target adapter. `plan.yaml.slices[]` carries only a `project`; the target (`name@vN`) is a denormalised copy of `project → adapter` and is **resolved on demand** from the bound project's topology rather than persisted. The 1:1 `project → target` invariant ("one target per project") is what makes the denormalisation removal safe. The integer `N` remains a load-bearing wire field wherever a resolved target *does* appear (`specify plan next`, slice `metadata.yaml`, the build request).

- `slices[].project` is optional on disk: omitted resolves to the sole project in the topology; a multi-project workspace requires it explicitly. The plan schema carries no `target` property — a slice may legitimately carry neither field.
- `propose.rs::resolve_target` is the single read-time resolver (`plan-reconcile-project-orphan` / `plan-reconcile-project-binding-required` / `plan-target-malformed`); `TargetRef` is constructed by it, never deserialised from `plan.yaml`.
- `specify plan validate` flags an omitted `project` only when a multi-project registry makes it ambiguous; `specify plan next` resolves best-effort and reports `target: null` rather than failing the lifecycle query — the build phase re-resolves before use.

## Operations typed at parse boundary

Adapter operations are typed Rust enums by the time YAML parsing finishes; string operation names never survive past the manifest loader. The decorative `operations:` array was removed from every manifest and schema — `operations()` returns the axis's closed WIT operation set, with the closed `SourceOperation` / `TargetOperation` enums (`crates/workflow/src/adapter/operation.rs`) as the typed sets carried by the axis-split `SourceAdapter` / `TargetAdapter` structs.

**Wire invariant.** The `source resolve` / `target resolve` envelopes' `operations: [...]` arrays iterate in kebab-alphabetical order (`["extract", "survey"]`, `["build", "merge", "shape"]`). Derived `Ord` on the enums is intentional because variants are declared in kebab-alphabetical wire order.

## Source operations

`specify source survey <source> [--plan <name>]` and `specify source extract <source> <lead> --slice <slice>` are the guest-routed source adapter operations (`orchestrate::survey` / `orchestrate::extract` — see §"Old-stack deletion" for the retirement of the two-phase native handlers). Resolution stays via `plan.yaml.sources.<key>`. The standing decisions:

- **Validate-before-visible.** An invalid lead set leaves `discovery.md` untouched; a failed Evidence validation leaves the slice in `refining`.
- **`discovery.md` stores raw, unmerged, per-source leads.** The runner stamps `source` from the surveyed source (attribution is CLI-owned). A re-survey is a per-source fold by `(source, lead)`, never a cross-source collapse — unification is deferred to plan time, so the same `lead` may legally appear under different source keys and alias-collision scoping is per `source`.

## Lead reconciliation

Agent-led cross-source lead reconciliation runs through a CLI-owned projection kernel (`Plan::propose_from`, kernel in `crates/workflow/src/change/plan/core/propose.rs`), driven by the guest `plan author` orchestration (see §"Plan-authoring collapse"; the native `plan propose --dry-run/--from` envelope pair retired at S4). The standing decisions:

- **Replaceable gate.** The kernel replaces slices only while the plan is replaceable (`lifecycle: pending` AND every entry `pending`; `plan-reconcile-plan-not-replaceable` otherwise). Re-propose wholesale-replaces all slices — a fresh projection, not a merge — discarding prior per-slice operator edits.
- **Coverage invariant, no kernel grouping.** The kernel carries no `scope` noun. It enforces total lead coverage (every surveyed `(source, lead)` referenced by at least one slice) plus at most one lead per source per slice. A lead may appear in more than one slice — fan-out is multiple ordinary slices joined by `depends-on`, and same-project multi-homing of a cross-cutting lead is equally legal (no `depends-on` implied). Same-source fusion is rejected on purpose: each surveyed lead is the source adapter's own sizing judgment, so merging two leads from one source would override that sizing; the operator owns same-source re-sizing at Gate 1 via `specify plan amend --sources`. The at-most-one-lead-per-source invariant is enforced at every writer, not just propose: `Plan::validate` carries the `duplicate-source-key` finding (folded into the validate-and-rollback gates inside `Plan::create` / `Plan::amend`), and the `plan amend --add-source` path re-gates via `reject_duplicate_source_keys` — a duplicate key would otherwise silently overwrite `evidence/<source>.yaml` at refine time. The kernel validates shape only — it never auto-merges, clusters, or forbids cross-source splits.
- **Explicit slice names.** Every response slice carries an explicit kebab-case `name` written verbatim; `depends-on` resolves against those names (cycles fail). Name uniqueness is the sole duplicate gate.
- **Project binding.** The agent binds each slice's `project` from the request's `projects[]`; an omitted `project` auto-binds only when exactly one project exists. The target adapter is **not** written to `plan.yaml` (see [§"Target adapter suffix policy"](#target-adapter-suffix-policy)).
- **Closed validation vocabulary.** `plan-reconcile-empty-catalog`, `-lead-orphan`, `-partition`, `-slice-source-collision`, `-slice-name-invalid`, `-slice-name-collision`, `-depends-on-cycle`, `-project-binding-required`, `-project-orphan`, `-plan-not-replaceable` — all `Error::Validation` outcomes (exit 2), not new enum arms.
- **Single-event journal.** One `plan.reconcile.completed` fires only after the `plan.yaml` write commits. The `/spec:plan` skill never calls `specify journal emit` for reconciliation.
- **Split on doubt.** Matching rides on per-source `synopsis` headlines alone, so the synopsis carries a contentfulness expectation (taught in survey briefs; surfaced as the non-blocking `discovery-lead-synopsis-thin` advisory). The error-cost asymmetry is stated in the propose brief: an over-merge is expensive and downstream-poisoning, an over-split is cheap and Gate-1-reversible — so a weakly-supported cross-source match stays as separate slices with the candidate pairing noted in `change.md` under `## Tentative merges`.
- **Deferred (rejected).** Kernel-side token-intersection auto-merge (shared slugs are unattested), kernel-side advisory clustering (would need per-lead `blocking-keys[]` survey metadata), and per-lead target-axis hints (`target` stays kernel-derived). Grouping uncertainty is the agent's to express through `change.md` prose, not a survey input signal.

## Target build envelope

`specify slice build <slice>` is guest-routed (`orchestrate::build` — see §"Old-stack deletion" for the retirement of the native two-phase handler and its `prepare.argv` / hook-script dispatch): request assembly, the report schema gate, the `target-build-*` aborts, the `slice.build.*` events, and the `built` transition all run inside the guest orchestrator; the bound target's guest owns code generation. The request/report DTOs and their gates live in `crates/workflow/src/slice/build/wire.rs`. The standing decisions:

- **Closed validation vocabulary.** The pinned `target-build-*` aborts — `target-build-request-schema`, `target-build-report-schema`, `target-build-success-with-blocking-finding`, `target-build-input-missing`, `target-build-output-missing` — are `Error::Validation` outcomes (exit 2), not new enum arms; adjacent operational diagnostics keep the family (`target-build-report-slice-mismatch`, `-failed`).
- **Cross-slice dependency is plan-level ordering** (`depends-on` + `specify plan next`), not envelope plumbing — there is no per-request cross-slice channel.
- **No merge envelope (v1).** `specify slice merge` stays the merge writer; `slice.merge.*` fire on its validator outcome, and the durable record stays `slice.archive.created`. A future merge-findings need reuses the build-report shape as `build/merge-report.yaml` rather than authoring a second schema.
- **Build outputs are not cached**; generated code is reproduced by re-running the build.

## Workspace terminology

The word **workspace** overloads three related concepts. Use them verbatim in operator-facing prose:

| Term               | Meaning                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Workspace**      | Registry-only platform repo: `workspace: true` in `project.yaml`, `registry.yaml`, plan artifacts at the repo root |
| **Workspace slot** | Materialised peer at `workspace/<project>/`                                                                        |
| **Workspace sync** | `specify workspace sync` — materialise slots and regenerate `topology.lock`                                        |

`/spec:init workspace` and `specify init --workspace` scaffold a workspace; init chains an initial workspace sync before returning.

## Plan-root override: global `--plan-dir` (env `SPECIFY_PLAN_DIR`)

Workspace routing runs phase work inside a materialised slot while `plan.yaml` / `change.md` / `discovery.md` stay at the initiating workspace — by design no slot grows its own plan, and symlinked slots physically live outside the workspace tree so upward path-walking cannot find it. The bridge is an **explicit pass-through from the executor**, which already knows the workspace root: the global `--plan-dir <PATH>` flag (env `SPECIFY_PLAN_DIR`) names the directory holding the governing plan artifacts.

- **One seam.** `Ctx::layout()` applies the override via `Layout::with_plan_dir`; only `plan_path()`, `change_brief_path()`, and `discovery_path()` move. Every `.specify/`-anchored path (slices, journal, scratch, cache, archive) stays on the project (slot) root — observability and slice state remain project-local.
- **Relative source bindings follow the plan.** `plan.yaml.sources.<key>.path` relative bindings are authored against the plan's home, so `resolve_source_path` joins them onto the plan root, not the slot.
- **Merge keeps its writer monopoly.** With the override, slot-side `specify slice merge` stamps per-entry `done` in the workspace plan — the "sole writer of `done`" contract holds in workspace mode without a second stamping verb at the workspace.
- **No back-pointer, no discovery.** The CLI never guesses: an override naming a plan-less directory fails with the same typed errors (e.g. `slice-synthesize-plan-missing`), whose message cites the overridden path. Adapter resolution is untouched — slot-side source adapters resolve project-locally (vendored tree or manifest cache) per §"Adapter loader axis routing".

## Slot adapter provisioning via workspace sync

Slots carry no plan and no adapters by design, yet slot-side phase work must resolve the adapters the workspace's `plan.yaml.sources` bind. The loader stays exactly as recorded (§"Adapter loader axis routing": resolution is project-local only); `specify workspace sync` provisions the probe location the loader already consults — it mirrors the workspace's adapter set (both axes, vendored tree and manifest-cache mirror alike, each adapter's `extension` included) into each synced slot's out-of-tree `<slot-cache>/manifests/{sources,targets}/`. Mirroring is unconditional over the workspace adapter set: no plan parsing in sync, and the cache is out-of-tree so slots carry no repo residue. Implementation: `crates/workflow/src/registry/workspace/mirror.rs`.

- **Per-name delete-then-copy, no GC of foreign names.** Each workspace-owned name is removed and re-copied per sync, so re-sync refreshes. Names the workspace does not own are never pruned — the slot cache has a second legitimate writer (`specify init` caches greenfield adapter seeds), and a per-axis wipe could delete an adapter only the slot has. A name present at the workspace in both probe locations copies from the manifest cache, matching the loader's probe order.
- **Slot-vendored names are skipped at mirror time, cross-axis.** The loader probes the cache *before* the vendored tree, so "the slot's own copy wins" cannot come from probe order — the mirror skips any name the slot vendors under `adapters/{sources,targets}/<name>/` on either axis. The same-axis skip keeps the slot copy winning resolution; the opposite-axis skip means the mirror can never manufacture an `adapter-name-axis-collision` in a previously healthy slot.
- **Local symlink slots are mirrored too** — unlike the contracts distribution, which skips them — because the adapter gap is slot-side resolution regardless of slot backing, and the write lands only under the peer's out-of-tree per-project cache. A `url: .` self-slot is skipped: mirroring the workspace onto itself would remove-then-copy the cache from itself. Peers without `.specify/` are skipped, never scaffolded.

The rejected alternative — a resolve-time plan-root fallback — shipped mid-run and was removed (`204e3867`): it contradicted the loader contract, keyed on the `adapter-not-found` string discriminant, and covered only the source axis. Staleness keeps its existing answer everywhere in workspace mode: re-run sync (the per-slice sync in the execute loop makes that automatic).

**Amendment (RFC-64/RFC-65):** the manifest mirror and vendored-tree mechanics above are historical. Post one-component-no-manifest, pinned identities resolve from the *global* single-file store (shared across projects — nothing to mirror) and development bare names resolve the sibling release build live. The only workspace-owned state a slot cannot reach on its own is the workspace's mirrored local components at `<ws-cache>/components/*.wasm`, so that is all `mirror.rs` copies today: per-file copy-over, foreign entries never pruned, a no-op when the workspace has no component cache.

## Registry projection and topology cache

Give every fact one writer; derive everything else. A project's *authored intent* — target `adapter` and `description` — lives only in its `.specify/project.yaml`. Its *routing identity* is **derived, not authored**: a deterministic structural projection of the project's own baseline. There are no `capabilities` / `keywords` facets — a derived routing identity needs no second writer duplicating what the baseline already states. `registry.yaml` carries membership + location, cross-project `contracts` wiring, and an optional `adapter` used solely as a greenfield scaffold seed.

- **Derived identity cache.** Workspace plan-time topology is projected through a committed `.specify/topology.lock` (`TopologyLock` in `crates/workflow/src/registry/topology.rs`), regenerated by `workspace sync` from each slot's `project.yaml` plus the deterministic baseline projection (`surface[]` = per-domain spec titles capped at `SURFACE_TITLE_CAP = 8`; `recent[]` = last `RECENT_TAIL = 10` `slice.archive.created` summaries). The projection is structural and byte-stable, never an LLM summary, so the committed lock verifies by regenerate-and-compare; it is machine-written write-if-changed and operators never hand-edit it. `TopologyProject` does `deny_unknown_fields`, so a pre-upgrade lock fails to load until `workspace sync` rewrites it — the ordinary machine-rewrite fix.
- **Read path.** `workspace_topology` builds `ProjectRef[]` from `topology.lock`, not `registry.yaml`; an absent cache fails `topology-cache-missing`. Empty `surface` / `recent` stay off the wire, so a greenfield project degrades cleanly to `description` only. A single regular project reads `project.yaml` plus its own projection live (`regular_topology`).
- **Staleness, not synchronisation.** `specify plan validate` emits `topology-cache-stale` (warning) on divergence — a regenerate-and-compare check whose fix is `workspace sync`. There is no top-down overwrite of `project.yaml` and no `--check` flag; CI uses the exit-2 gate of `plan validate`. Both topology codes are plan-doctor findings on exit 2.

## Tool-owned schemas

Every JSON Schema is owned by the repo of the WASI tool (or the CLI) that runs it. Plugin briefs reference schemas exclusively by their canonical `$id` URL and never contain schema bodies. The three Vectis runtime schemas live solely with the vectis extension crate in `augentic/specify-adapters` (`targets/vectis/extension/schemas/`), with no byte-identity duplication or manual mirroring obligation; this repo no longer carries any vectis schema body.

Tool-owned schemas use a stable `$id` of the form `https://schemas.specify.dev/<tool>/<name>.schema.json`. The URL is a logical identifier; it does not need to resolve to a hosted copy. CLI-owned framework schemas use `https://schemas.specify.dev/specify/<path>`. The `links.brief-schema-link-resolve` predicate enforces that every `schemas.specify.dev` URL cited in adapter briefs resolves to a known schema.

An operator-curated file at `.specify/design-system/components.yaml` declares shared UI components (`status: confirmed | rejected`); schema CLI-owned at `schemas/design-system/components.schema.json`, domain type `ComponentsCatalog` in `crates/workflow/src/design_system.rs`. ## Standards layer split into `specify-standards` and `specify-schema`

The standards surface (rules parser / resolver, `WorkspaceModel`, indexer, deterministic hint interpreter, `specify lint` runner) lives in `specify-standards`, a **sibling** of `specify-workflow` rather than a module inside it. `specify-schema` is the shared leaf owning every embedded JSON Schema constant plus the `jsonschema` plumbing, so workflow and standards consume schemas from one place.

Dependency direction is the decision: `specify-standards` does **not** depend on `specify-workflow`, and `specify-workflow` does **not** depend on `specify-standards`. The sibling shape makes "no lifecycle authority in review" a type-system invariant — review code cannot reach slice or plan transitions because the workflow types are not visible. The `kind: tool` lint evaluator is wired through a `ToolRunner` trait at the CLI boundary, not a `specify-registry` dependency. The neutral diagnostic substrate lives one layer further down in `specify-diagnostics` (see [§"Drained `Error::Validation` and the `Diagnostic` substrate"](#drained-errorvalidation-and-the-diagnostic-substrate)), so `specify-workflow` and the `specify_model::validate` registry mint diagnostics without depending on anything named `lint`. The root binary wires the halves together at the dispatcher boundary; they never call each other directly. See [architecture.md §"Standards layer vs workflow layer"](./docs/standards/architecture.md#standards-layer-vs-workflow-layer).

## Drained `Error::Validation` and the `Diagnostic` substrate

Every check surface — `specify lint`, `specify lint framework`, `specify slice validate`, plan validation, library validators — speaks one currency: `Diagnostic` / `DiagnosticReport`, housed in the `specify-diagnostics` leaf (depends only on `specify-{error,schema,digest}`; must never depend on standards, model, or workflow so it stays importable by every producer).

**Lint and validate stay conceptually distinct surfaces.** They share the substrate, not the authority: **validate** gates a lifecycle transition — workflow-owned, non-negotiable, non-silenceable (ignore directives are off). **lint** is standards/policy compliance — codex-owned, lifecycle-neutral (may block CI, never transitions a slice), silenceable with an in-source rationale. Convergence applies to the data type, fingerprint, validator, renderer, and blocking predicate — never to the concepts or their gate policies. The litmus test: `validate` (or any non-lint producer) must not depend on a crate or module named `lint`.

**Two orthogonal axes** keep the concepts queryable on the one type: `source` (provenance: `deterministic | model-assisted | hybrid | human | tool`) and `kind` (nature: `violation` vs `review` — a deterministically-raised request for judgment; the former `Deferred` classification and `lint-mode: model-assisted` rules both surface as `kind: review`, `source: deterministic`).

**Uniform blocking predicate, per-surface application.** `blocking()` returns true iff `kind == violation && status == open && severity ∈ {critical, important}`. `kind == review` never blocks anywhere. Each surface applies the same predicate, differing only in whether ignore directives run first (lint: yes; validate: no).

**`Error::Validation` is payload-free.** `Error::Validation { code, detail }`; `variant_str()` returns the carried `code`, so the top-level wire `error` is the specific discriminant rather than a generic `"validation"`. Handlers own rendering: a gate failure renders the full `DiagnosticReport` on **stdout**, then returns the payload-free error purely to carry exit 2 and the discriminant on stderr. Single operational errors that are not findings take the same shape via `Error::validation_failed(code, detail)` but render no report.

**Widened `ruleId` namespace.** The diagnostic `ruleId` pattern accepts both the closed codex family (`UNI-`/`CORE-`/… `-NNN`) and the runtime-validation discriminant form (dotted/kebab lowercase), so workflow and validate producers stamp their invariant ids onto the same finding shape the codex engine uses.

## Composition validation is vectis-tool-owned

The `specify_model::validate` registry carries no `composition` rule namespace. The registry once registered four `composition.*` rules, but `validate_slice`'s canonical artifact set never fed them — they were dead at the runner while their unit tests asserted the registry entry existed (false confidence). Rather than wiring `composition.yaml` into `CANONICAL_ARTIFACTS`, the namespace was deleted: deep composition validation (schema, structural identity, token/asset refs, catalog cross-references) is owned by the vectis WASI tool's `validate composition` mode, and a shallow host-side duplicate would only drift from it. The host keeps exactly one composition touchpoint: `cross.composition-maps-to-consistent`, which checks `maps_to` well-formedness against the slice's specs. `Artifact::Composition` survives in `specify-diagnostics` — the vectis tool and build wire still stamp findings with it.

## Codex-rule schema: one source of truth

The rules parser consumes the canonical rule schema directly via `specify_schema::RULE_JSON_SCHEMA` (paired with the typed `Rule` DTO). One source of truth means no vendored copy and no drift check: the canonical schema lives at `schemas/rules/rule.schema.json` and is embedded through `specify-schema` like every other schema.

## Lint finding status, disposition, and exit

`Diagnostic.status` is a closed kebab-case enum. The fingerprint algorithm excludes both `status` and `disposition`, so demoting a finding from `open` to `ignored` (or `false-positive`) never changes its identity.

| Value            | Set by            | Meaning                                                                                                                              |
| ---------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `open`           | scanner (default) | Freshly emitted finding before post-passes run. The only value that contributes to the `specify lint` exit-code decision by default. |
| `ignored`        | directive pass    | An in-source `specify-ignore` directive matched the finding's `(path, line, rule-id)`. Carries `disposition.directive`.              |
| `false-positive` | directive pass    | A directive matched and the rationale was prefixed `false-positive:`. Reported separately in dashboards.                             |
| `fixed`          | reserved          | Reserved for the cross-run baseline diff verb. No producer in v1.                                                                    |
| `accepted`       | reserved          | Reserved for explicit operator acceptance via the baseline file. No producer in v1.                                                  |

`disposition` is an optional sibling object (`{ source, directive?, since? }`), populated only when `status != open`; `disposition.source` is a closed enum whose only v1 value is `directive` — a future baseline producer adds `baseline` additively.

Lint resolves the process exit with **status-aware severity** (recorded for `specify lint project`, retired from the operational surface with RFC-65; `specify lint framework` inherits the same rule): exit `2` only when a finding has `status: open` AND `severity ∈ {critical, important}`. The synthetic findings for malformed (`UNI-022`) and orphan (`UNI-023`) directives default to `status: open` (the shared codex ships both at `important`). **Graceful degradation:** when the codex resolver does not produce `UNI-022`/`UNI-023` — a consumer without the shared codex tree — synthetic emission silently skips while status stamping continues; the fix is codex distribution (see [§"Shared codex distribution"](#shared-codex-distribution)). The operator-facing directive grammar lives in the parent repo's [`docs/reference/ignore-directives.md`](https://github.com/augentic/specify/blob/main/docs/reference/ignore-directives.md).

## Shared codex distribution

> **Superseded (distribution half)** by [§"Codex ownership flip: shared packs embed in the binary (RFC-66)"](#codex-ownership-flip-shared-packs-embed-in-the-binary-rfc-66): the packs now compile into the binary and materialize from the embed — the adapter-ancestor walk and its fail-soft path are deleted. The probe order and the distribution-vs-evaluation split below remain in force.

Consumer projects resolve shared `UNI-*` rules without a co-located framework checkout or a manual `--rules-root` (RM-07). The shared codex is authored in this repo (`codex/rules/{universal,core}/`) and compiled into the binary; `specify init` and `specify adapters sync` (which absorbed the retired `rules sync`) materialize it into the out-of-tree `<project-cache>/codex/`, **pinned to the binary version**.

- **Probe order** (`probe_rules_root` in `crates/standards/src/rules/resolve.rs`): explicit `--rules-root` → monorepo `codex/rules/universal/` → codex cache → `rules-root-required`. The cache rung is a derived root, so the fallback overlay stays skipped, exactly like the monorepo case; both `specify lint` and `specify rules export` honour it.
- **Distribution.** `cache_codex` / `sync_codex` write the embedded packs into the cache (`universal/` always, `core/` under `--include-framework`). Materialization from the embed cannot miss, so there is no fail-soft path; a stale stamp re-materializes on the next provisioning invocation.
- **Provenance.** `CodexMeta` (`codex-meta.yaml`) records the binary version, `include_framework`, and `fetched_at`. Audit-only; the resolver never reads it.
- **Distribution vs evaluation are independent.** `--include-framework` controls what lands in the cache; the resolver's `include_core` controls whether `CORE-*` rules are evaluated/exported. Consumer projects default to neither.

## Single slice-model artifact

- **One artifact.** A synthesized slice persists exactly one structured file, `model.yaml`, with provenance inline (`requirements[].claims[]` carrying `winner`, plus `resolution`). There is no on-disk `provenance.yaml`.
- **Provenance is a projection.** `ProvenanceIndex` (`crates/workflow/src/slice/provenance.rs`) is computed from `model.yaml` and emitted on demand by `specify slice provenance`; it is never loaded from disk. There is no file-drift gate (a projection cannot drift from its source); spec-vs-model staleness and `(source, id)` orphan checks apply. There is no `slice.provenance.written` journal kind.
- **One schema.** `SLICE_MODEL_JSON_SCHEMA` validates both the agent's synthesis-response `model` and the persisted file; kernel-owned fields are optional, re-derived, and ignored if supplied (normalize, never reject), so `DRAFT_MODEL_JSON_SCHEMA` and the `slice-synthesize-kernel-field-usurped` abort both retire.

## Projection over persistence

Derived state is projected on demand from the journal plus committed artifacts — or pinned to its single authored home by lint — never persisted as a second hand-maintained copy. A projection cannot drift from its source; a persisted copy drifts the moment the source moves.

- **The journal is the anchor.** `.specify/journal.jsonl` ([§"Journal event names"](#journal-event-names)) plus the committed artifacts (`plan.yaml`, slice `metadata.yaml`, the specs baseline) are the only stores; everything downstream is recomputed per invocation.
- **Live projections.** Provenance ([§"Single slice-model artifact"](#single-slice-model-artifact) — "Provenance is a projection") and `specify plan status`, which projects plan entries + the candidate slice's lifecycle + the journal tail into a deterministic `next-action` with stop classification read from the `slice.synthesize.failed` / `slice.build.failed` / `slice.merge.failed` terminals, writing nothing and emitting no event. RM-15's re-entry fields extend the same body rather than persisting a status file.
- **One read surface.** `specify journal show [--filter <event-id-prefix>] [--limit N]` is the read verb over the journal; eval probes and any future dashboard consume it instead of bespoke `jq` bridges over the JSONL.
- **Lint-pinned homes.** Where derived prose must exist as a copy (the eval catalog's status table), a framework rule pins it to its authored home (CORE-056 catalog↔runs agreement) so divergence is a lint finding, not a review discovery. (The `content-digest-eq` digest-pinning kind retired with its last rule consumers — restatements became links.)

## Slice synthesis engine

The durable contract for the slice synthesis kernel and its schema/event additions. Complements [§"Single slice-model artifact"](#single-slice-model-artifact) and [§"Authority: document-level plus one override (v1)"](#authority-document-level-plus-one-override-v1). The kernel-ownership split (agent authors claims + prose; kernel re-derives ids, status, winners, sources, provenance) is pinned in [workflow.md §"Slice synthesis"](./docs/standards/workflow.md#slice-synthesis); the guest `slice refine` / `plan execute` orchestrations are the kernel's only drivers (the native `slice synthesize --dry-run/--from` envelope pair retired at S4 — see §"Old-stack deletion"). The standing decisions:

- **Judgment-dispatched.** There is no WASI tool path and no closed *request* wire shape. Authority is resolved by the kernel **after** the response returns, never shipped in the inputs envelope.
- **Authority kernel.** Resolution order per `(source, kind)`: per-slice override → document `authority` → default class order; a tie at the top class is a `conflict`; mixed-kind requirements resolve each claim independently and pick the strictly-greatest effective class. Pure modules under `crates/workflow/src/slice/synthesis/` (`authority.rs`, `project.rs`, `render.rs`, `wire.rs`).
- **Earned-core schema trim.** `model.schema.json` is trimmed to `required: [requirements, tasks]` — the deferred `domain` / `apis` / `configuration` / `technical-logic` / `observability` sub-trees and their id grammars, `value` / `path` on claims, and `resolution` / `resolution-trace` are dropped until earned. `synthesis.schema.json` `$ref`s the model schema by relative URI; the two compile together through a `jsonschema::Registry` pinning `MODEL_SCHEMA_URL`. The `validate_synthesis_json` gate runs on raw bytes before structural deserialize (`synthesis-schema`, exit 2).
- **`to_provenance_index` recompute.** With `value` / `path` / `resolution` gone from the model, the projection recomputes `resolution` via the authority kernel and reads each claim's `value` / `path` from on-disk Evidence keyed by `(source, id)`.
- **Drift validators.** `specify slice validate` emits seven blocking typed-model findings (exit 2) — `slice-model-schema`, `slice-spec-provenance-stale`, `slice-model-target-drift`, `slice-model-source-orphan`, `slice-model-cross-ref-orphan`, `slice-model-claim-kind-mismatch`, `slice-model-id-grammar` — as `Diagnostic` findings on the `DiagnosticReport` surface (meanings tabulated in [workflow.md §"Slice synthesis"](./docs/standards/workflow.md#slice-synthesis)).
- **Journal events.** The `slice.synthesize.{started|agent|completed|failed}` lifecycle quartet is distinct from the per-requirement `slice.synthesis.{conflict,divergence,unknown}` tag events. See [§"Journal event names"](#journal-event-names).

## `domain` replaces `unit` as the spec.md boundary noun

The slice-sized spec grouping — the `specs/<slug>/spec.md` directory segment, the `proposal.md` section heading, and the owning key on each model requirement — is named **domain**, not *unit*. *Unit* was target-neutral but colourless and collided with "unit test" prose; *domain* survives all three first-party targets (Omnia crate/service surface, Vectis business feature, contracts API domain) and was already latent in the contracts shape brief ("API domain slug"). The rename was a hard cut with no migrator (pre-1.0, no downstream projects): the wire keys (`synthesis.schema.json` / `model.schema.json` `domain`, `topology-lock.schema.json` / `proposal.schema.json` `surface[].domain`), the `## Domains` proposal heading, and the validate rule ids (`proposal.domains-listed`, `cross.proposal-domains-have-specs`) all renamed in place with no compatibility aliases. Note the name proximity to the *deferred* top-level `domain` sub-tree in the earned-core schema trim (§"Slice synthesis engine"): the requirement-level `domain` key is the spec grouping; the deferred sub-tree, if ever earned, must pick a non-colliding name.

## History via git plus an outcome ledger

Revises the archive posture. The durable record of merged work is git history of the committed `.specify/specs/` baseline plus an append-only outcome ledger: a `slice.archive.created` journal event (payload: slice, touched-specs, outcome summary, merge SHA) emitted from the merge path. ## Bootstrap and upgrade lifecycle

The standing record for the two CLI-owned bootstrap concerns — stale binary and plugin-cache drift. The `/spec:init` skill stays the orchestrator; each deterministic action is its own CLI verb (`upgrade`, `plugins {doctor,refresh}`; handlers under `src/runtime/commands/`, domain logic under `crates/workflow/src/`).

- **No migration framework, pre-1.0.** There are no compatibility shims, no versioned parsing, and no `specify migrate` verb: a major version cut means re-init (`specify init --upgrade` over an existing project bumps the pin; anything deeper is a fresh `specify init`). A pin older than the binary loads normally; only a pin *newer* than the binary refuses (`Error::CliTooOld`, exit 3). If a migration story is ever warranted post-1.0, it gets its own decision here first.
- **CLI owns the deterministic actions; skills orchestrate intent and consent only.** Every mutating action requires `--yes` (or interactive confirmation); `--dry-run` previews without writing; the read-only probe (`plugins doctor`) never mutates.
- **Channel detection.** `InstallChannel::detect()` classifies the running binary's path into `cargo | brew | binary | unknown` (the last a structured diagnostic with manual-upgrade guidance). The latest-release probe order is `SPECIFY_RELEASE_TAG` override → `gh release view` → unauthenticated GitHub API; a probe failure is a **warning**, not an error.
- **Plugin-cache sha derivation.** `plugins doctor` scans `$CURSOR_HOME/plugins/cache/` against the discovered marketplace; the expected sha for relative-path sources is `git rev-parse HEAD` of the marketplace repo, shared by every plugin. An unresolvable expected sha degrades to `present` / `missing` rather than asserting unprovable drift. The closed status set is `ok | drifted | present | missing | extra`; `doctor` never exits non-zero on drift (drift is a finding), only on FS/parse failure. `plugins refresh` deletes the cache directory, journals `plugins.refreshed`, and never restarts Cursor or touches IDE state.
- **Two bootstrap journal events** — `cli.upgraded`, `plugins.refreshed` (see [§"Journal event names"](#journal-event-names)). `--dry-run` writes nothing and fires no event.
- **Binary-channel self-replace deferred.** The `cargo` and `brew` executors are fully wired; the `binary`-channel in-process self-replace (download → verify checksum sidecar → atomic swap) is deferred until the release pipeline's archive/checksum naming contract lands. Today the `binary` channel emits a planned-action plus structured manual-upgrade guidance.

## Workspace git transport from the guest (RFC-65)

**Decision (2026-07).** RFC-65 routes `workspace sync` / `workspace push` (and `workspace prepare` with them — an addition beyond the RFC's literal sync/push row, carried because prepare shares the same git surface) into the core guest, whose `workflow` world deliberately holds no network, no sockets, and no subprocess capability — yet the workspace verbs are today a pure subprocess-`git` surface: every operation funnels through the `cmd::git` boundary (`crates/workflow/src/cmd.rs`) into `crates/workflow/src/registry/workspace/` (sync, push, bootstrap, mirror) and `crates/workflow/src/registry/branch/` (prepare). The RFC named three candidate mechanisms (host capability, wasm-native git, the model backend's agent) and pinned none; this entry pins the mechanism. **The pinned mechanism is a generic, domain-free host git capability**: an Omnia host crate in the existing `wasi-*` family (working title `wasi-git`, interface `omnia:git/cli`) whose one operation executes the host machine's `git` binary on the guest's behalf — argv-shaped, root-scoped by deployment configuration, hardened non-interactive host-side. Implementation may follow the RFC-65 cut separately (last bullet).

The surface being carried, from today's native implementation: **sync** — `clone --bare` into the out-of-tree per-URL mirror (`specify_schema::cache::mirror_dir`), `config remote.origin.fetch`, `fetch origin` (mirror and slot), `worktree prune` / `worktree add --detach --force`, `remote get-url origin`, plus the greenfield bootstrap leg (`init`, `remote add origin`, `add .`, `status --porcelain`, `log --oneline -1`, identity-pinned `commit --no-gpg-sign` and `commit --amend --no-gpg-sign`); **push** — `rev-parse --is-inside-work-tree`, `symbolic-ref HEAD`, `status --porcelain=v1 --untracked-files=all`, `remote set-head origin --auto`, `symbolic-ref refs/remotes/origin/HEAD`, `ls-remote --symref origin HEAD`, `ls-remote --heads origin refs/heads/<branch>`, `rev-parse HEAD`, and the publish itself — `push --force-with-lease=refs/heads/<branch>:<sha> -u origin <refspec>`; **prepare** — `fetch origin`, `checkout` / `checkout -b specify/<change> origin/HEAD`, `merge --ff-only`, `show-ref --verify`, `merge-base --is-ancestor`. Three properties of that inventory drove the pin: it is wide (~20 subcommands) and still evolving; roughly half is local object-database work against the mounted workspace tree and the out-of-tree mirror, not network transport; and remote auth is entirely delegated — credential helpers, `ssh-agent`, and `~/.gitconfig` are host processes and host state that git consults itself, so any in-guest transport would have to re-solve auth from scratch.

- **The shape: one argv operation mirroring `cmd::git`, not a typed per-operation WIT contract.** `run(cwd, argv) -> result<output, error>` carries exactly what `cmd::git` builds today (`git -C <cwd> <args>` plus the identity-pinned `git_as_specify` variant, expressible as `-c` argv). A closed per-operation contract (`fetch`, `push`, `worktree-add`, …) would freeze Specify's git workflow into Omnia's WIT — precisely the domain leakage the "Omnia stays domain-free" invariant forbids — and would need re-cutting every time the workspace module grows a subcommand. The argv shape models *the git tool*, like `wasi:http` models HTTP; Specify's use of it stays in the guest.
- **Root-scoped, not generic exec.** A generic exec capability is rejected outright: arbitrary subprocess is ambient host authority and would void every fence at once. The git capability is bounded on three axes the host enforces: the binary is fixed (`git`, never guest-named); `cwd` must resolve beneath a root the deployment configuration grants (the generated manifest's `[[mount]]` project root plus a manifest-granted mirrors root for `mirror_dir`); and the environment is not passed through. Network egress exists only as git transport to remotes named in the operator's committed `registry.yaml` — mediated, enumerable, and observable, never an ambient `wasi:http` / `wasi:sockets` grant on the workflow world.
- **Credentials stay host-side.** The host git binary consults the operator's credential helpers, `ssh-agent`, and `~/.gitconfig` exactly as the native verbs do today; no token, key, or helper output ever crosses the seam into the guest. This is the decisive advantage over both rejected options.
- **Non-interactive by construction.** The host wrapper pins `GIT_TERMINAL_PROMPT=0`, disables askpass, and runs ssh in batch mode; a credential miss is a typed capability error the guest maps onto the existing `workspace-git-*` diagnostic family, never a prompt. This preserves the hydration kernel's non-interactive property on the workflow side: cloud and CI runs fail loudly instead of hanging.
- **Rejected: wasm-native git in-guest (gitoxide on wasm32-wasip2).** The local object-database half is plausible, but the transport half is not: gitoxide's HTTP transports assume native TLS stacks, SSH transport spawns an `ssh` subprocess the guest cannot have, and a `wasi:http`-backed transport does not exist and would hand the workflow world the ambient network grant the guest-never-fetches posture exists to prevent. Auth is worse still — credential helpers are subprocesses, so secrets would have to enter the guest as configuration, moving credentials to the wrong side of the seam. Add the binary-size cost and the `git worktree` semantics the mirror scheme depends on, and the option fails on every axis except purity.
- **Rejected: the model backend's agent.** Routing `git push` through a judgment leg (cursor-agent executing git in the lent workspace) makes a deterministic, mechanical operation non-deterministic, unauditable, and model-priced; it requires `cursor-agent` and model access in CI for what is today a subprocess call; and it inverts the architecture — judgment legs exist for judgment, not transport. The agent also cannot reach the out-of-tree mirror or honour the `--force-with-lease` discipline reliably. Rejected without reservation.
- **Invariants preserved.** The host layer stays Specify-free: `wasi-git` carries git vocabulary only, is generic Omnia surface (any guest may link it), and nothing Specify-shaped enters Omnia. The guest never gains ambient network: the workflow world's only egress remains mediated capability calls. The provisioning surface does not regrow a runtime role: the workspace verbs move guest-side rather than staying native for convenience. The guest-never-hydrates fence is untouched — the git capability reaches *project remotes* declared in `registry.yaml`, never adapter registries or the global store.
- **Implementation sketch.** Omnia side: a new `wasi-git` host crate following the `wasi-*` pattern (host trait, default impl shelling to host git with the hardening above, allowed-roots from deployment config). Specify side: `wit/specify.wit`'s `workflow` world gains `import omnia:git/cli;`; the generated deployment manifest links the capability and grants the project mount plus the mirrors root; `crates/workflow/src/cmd.rs` is the port seam — the `CmdRunner` boundary lowers to the capability import on `wasm32` and keeps `std::process::Command` off it, so `registry/workspace/` (sync, push, bootstrap, mirror) and `registry/branch/` (prepare) port without rewriting call sites. A later consequence, not scope: the guest merge's skipped git commit leg (§"Deterministic guest merge", `slice.merge.commit-skipped`) regains its commit through the same capability.
- **Implementation may follow the RFC-65 cut separately.** This entry satisfies the RFC's landing condition ("this RFC does not land until that mechanism is pinned, even if its implementation follows separately"). In the interim `workspace sync` / `push` / `prepare` remain native residue on the shipped binary — the one acknowledged trailing item against RFC-65 acceptance criterion 3 (the exact native verb set) — and they flip guest-side in the change that lands `wasi-git` and the world import, with no operator-visible behavior change beyond the routing.

## Codex ownership flip: shared packs embed in the binary (RFC-66)

**Decision (2026-07).** Supersedes the distribution half of [§"Shared codex distribution"](#shared-codex-distribution): the shared codex no longer travels beside an adapter source checkout. The `universal/` and `core/` packs (`codex/rules/{universal,core}/` at the repo root) are compiled into `specify-workflow` at build time (`crates/workflow/build.rs` stages every pack `.md` into a generated `OUT_DIR/codex_packs.rs` static table, `include!`d by the materializer in `crates/workflow/src/init/cache.rs`) — the same embed posture as the JSON Schemas in `specify-schema`. The codex's only version knob is the binary's.

- **Materialization replaces the ancestor walk.** `cache_codex` / `sync_codex` write the embedded packs into the unchanged cache layout (`<project-cache>/codex/codex/rules/{universal,core}/`); `rules_root_for_component` (the adapter-ancestor walk) and the fail-soft "no source found" path are deleted — materialization from the embed cannot miss, so the functions return the stamped `CodexMeta` instead of a distributed/not bool. The resolver's probe order, `SHARED_REL` / `CORE_REL` constants, and derived-root semantics are byte-identical; the monorepo probe rung stays ahead of the cache rung, so framework repos keep linting their working trees, not an embed.
- **`CodexMeta` re-pins to the binary version.** The `codex-meta.yaml` `source` field records the workflow crate's `CARGO_PKG_VERSION` (the workspace version) instead of an adapter source/ref. Materialization compares the recorded `(source, include_framework)` stamp against the running binary and re-materializes on any mismatch — cheap, since the bytes are already in memory. `--include-framework` semantics are unchanged: `core/` lands only when asked.
- **`specify rules sync` survives, adapter-independent.** The verb no longer resolves an adapter: the `--source` flag and the `rules-sync-no-adapter` error are deleted, and the verb works on adapter-less workspace projects too. Verb retirement is deferred to the RFC-65 `adapters sync` integration (RFC-66 sequencing: the verb retires only when `adapters sync` absorbs re-materialization). **Amendment (RFC-65):** that retirement landed — `specify adapters sync` absorbed codex re-materialization and `rules sync` is gone (see [§"The provisioning front (RFC-65 move 5, amending D-bin)"](#the-provisioning-front-rfc-65-move-5-amending-d-bin)).
- **Init keeps distributing.** Regular `specify init` materializes the embed inline (its `codex-present` envelope field is now always `true`); workspace init still distributes no codex at init time.
- **Overlay half: components carry their rules; extraction is deferred.** Every adapter's prose registry now embeds its `prose/rules/` tree into the published component (contracts and documentation joined omnia and vectis in `specify-adapters`), so an overlay pack is pinned to the adapter version by construction — it travels inside the artifact that has the identity. The engine-side extraction of that embedded tree into the resolver's manifest-cache overlay rung (`<project-cache>/manifests/{sources,targets}/<name>/prose/rules/`) is **deferred**: the pinned WIT surface has no docs-enumeration export, and the component's MCP references server is reachable only inside a composed deployment — neither of which resolve-time extraction can use today. Extraction rides a future `adapters sync` / MCP-references leg (or a WIT revision); with `lint project` retired from the operational surface and the manifest-cache overlay rung gone, the deferral currently has no engine-side consumer — overlay rules reach consumers through `specify rules export` when the surface returns.

## Publishing and distribution: one transport, idempotent legs (RFC-66)

**Decision (2026-07).** Every wasm-shaped artifact — the adapter components, the core guest, the WIT contract — publishes over **one transport**: wasm-pkg/OCI behind the static well-known file at `https://augentic.io/.well-known/wasm-pkg/registry.json`. There is no registry service: the well-known file maps the first-party namespace to the backing OCI registry, consumers (including `install_tofu` and plain `wkg get`) resolve it automatically, and consume auth is nothing — first-party packages are public and pull anonymously on a fresh machine. The backing registry is an implementation detail named only in the workflows and the well-known file itself; `augentic.io` and the `specify:` identities are the stable surface, and migrating hosts is editing one JSON file and re-pushing packages. (RFC-66 — landed; removed from the tree, recoverable from git history.)

- **Idempotency is the immutability enforcement.** Every publish leg is probe-first (`scripts/wkg-publish-idempotent.sh` — a semantically identical sibling copy lives in `specify-adapters`): probe the registry for the exact identity, skip when present, build-and-push only on a definitive not-found. Skip-if-present is what prevents a re-tag or workflow re-run from mutating a published version, and it doubles as the version-changed guard (a tag that bumped nothing finds every identity present and pushes nothing). The probe must distinguish *absent* from *unreachable*: only a not-found fingerprint in the probe output grants permission to publish; any other failure aborts the leg non-zero, because guessing "absent" against an unreachable registry would re-push into an immutable identity. The fingerprints are coupled to `wkg`'s error text, so CI pins `cargo install wkg@0.15.0 --locked` — revalidate the fingerprints when bumping.
- **The binary↔core lockstep.** The `v*` tag publishes `specify:core@<VERSION>` (a job-level guard asserts the tag matches the `VERSION` file) and the `release` job carries `needs: [build, publish-core]`: a release whose core push failed never attaches binaries — a broken core publish is a failed release, not a binary-only release. `publish-wit` gates nothing: the WIT versions independently and most tags no-op that leg. The core publish is load-bearing since RFC-65 move 4: a released binary hydrates and resolves exactly this identity (see [§"Core versioned by the binary"](#core-versioned-by-the-binary-rfc-65-move-4-amending-d-dist)).
- **Publish auth is `GITHUB_TOKEN` only.** Both repos' workflows write a wkg config from `permissions: packages: write` + `GITHUB_TOKEN`; the `SPECIFY_REGISTRY_USERNAME` / `SPECIFY_REGISTRY_PASSWORD` secrets are retired. Every publish leg lives in a `cargo make publish-*` task (`publish-core`, `publish-wit` here; `publish-adapters` in the adapters repo) and the workflow is a thin caller, so local emergency publishing is the same code path with a developer's own token.
- **WIT ownership becomes real.** This repo owns and publishes `specify:adapter` from `wit/specify.wit`; `specify-adapters` deleted its root copy and vendors the published package at `wit/deps/specify/specify.wit`, pinned in exactly one place (its `WIT_PIN`) and refreshed by `cargo make wit-vendor` (with a `wit-vendor-sibling` dev override for iterating on a contract change before publish). Its `check-pins` WIT arm verifies vendored bytes against the pinned published version — deterministic in CI without a sibling checkout — and skips gracefully until the first publish lands; the RFC-64 sibling-`cmp` migration carve-out is deleted. The copy-parity discipline between the repos is dead: one owner, everything else consumes.

## Adapter hydration, the committed lock, and the generated deployment (RFC-65)

**Decision (2026-07).** The provisioning half of [RFC-65](rfcs/rfc-65-standalone-deployment.md) lands as one surface-agnostic hydration kernel plus one manifest generator. `hydrate(project_dir, refs, frozen, fetch)` (`crates/workflow/src/hydrate.rs`) resolves every declared pinned identity — the `project.yaml.adapter` pin, the `adapters:` prefetch list, and `plan.yaml` source pins via `collect_refs` — against the global store, pulling on miss through an **injected fetch leg**: the root binary composes `registry::store::install_tofu`, so `specify-workflow` stays wasmtime- and network-free and the guest-never-hydrates fence is a dependency-direction invariant, not a convention. Two triggers share the kernel (`specify init` and `specify adapters sync`); no prompt exists at or below it.

- **`.specify/adapters.lock` semantics.** The committed cross-machine digest pin (`hydrate::lock::AdaptersLock` — versioned YAML mapping `<name>@<version>` to its `sha256:<hex>` component-byte digest, sorted, machine-written). Verify-when-carried: a resolved entry whose digest diverges from the committed pin is the typed `adapter-digest-mismatch` naming the identity and both digests. Append-on-first-install: an identity the lock does not carry is pinned after it resolves clean. Write-if-changed: the lock is written back atomically once per hydration, and only when it gained entries — a clean re-verify leaves it byte- and mtime-stable. Frozen-read-only: `--frozen` turns a store miss into the typed `adapter-not-installed` and never appends or writes the lock, so strict-CI reproducibility runs cannot mutate the committed artifact. Undeclared entries are left in place (store entries are immutable and shared across projects).
- **Lock verification is enforced at every manifest-producing path, not just the provisioning triggers.** The drive-time regeneration (`src/runtime/commands/deploy.rs::discover`, run by the guest leg before every drive) re-verifies each pinned entry — bound adapters and prefetch pins alike — through the kernel's shared pair `hydrate::verify_resolved` (RFC-48 D4 verify-on-read) + `hydrate::verify_locked` (the read-only lock gate), so a warm-but-divergent store populated by another project or machine aborts with `adapter-digest-mismatch` before any manifest is written or guest driven. This anchors acceptance criterion 8's "before any guest loads" at both the provisioning triggers and the drive; the drive never writes the lock.
- **The generated manifest is the sole deployment description.** After hydration (and on every drive), `specify_workflow::deploy::generate` renders the deployment manifest atomically into the per-project cache (`<project-cache>/deployment/omnia.toml`): one `[[guest]]` per resolved component — pinned store entries and project-local bare-name components alike — plus the core guest's link allow-list, the writable `"."` mount, and per-adapter `/mcp/<name>` routes. The generator verifies every referenced component exists before writing (a dangling pinned entry is `adapter-not-installed` naming the identity and the literal sync command — the store is load-bearing), and host paths are emitted as fully escaped TOML basic strings (backslash, quote, and control characters). The manifest is derived, never committed, never hand-edited; a project-root `omnia.toml` still wins wholesale as the developer posture.

## The provisioning front (RFC-65 move 5, amending D-bin)

**Decision (2026-07).** Amends [§"One `specify` binary"](#one-specify-binary-triage-main-over-omniarun-rfc-61-step-5-milestone-s3-decision-d-bin): the triage main is replaced by a **provisioning front**. `runtime::run` no longer parses the shared grammar — it triages on argv[1] alone against the closed native token set (`init`, `adapters`, `upgrade`, `plugins`, `workspace`, plus the hidden `lint`) and parses only those through a narrow provisioning-only clap grammar (`src/runtime/cli.rs`, reusing the shared `InitArgs` / `UpgradeArgs` structs); **every other argv forwards unparsed** to the workflow guest through `specify_runtime::drive` and the generated manifest, `--help` / `--version` / bare invocation included. Native provisioning verbs keep their envelopes; forwarded verbs inherit stdio and pass exit codes through verbatim (0/1/2/3, including clap's usage-error 2 via the guest shim's `try_parse` + `clap::Error::exit_code()` through the p3 exit).

- **The native set.** `{init, adapters sync, upgrade, plugins}` per RFC-65 acceptance criterion 3, plus the acknowledged `workspace sync/push/prepare` residue (see [§"Workspace git transport from the guest (RFC-65)"](#workspace-git-transport-from-the-guest-rfc-65)) and `lint framework` as native-but-hidden framework-repo dev tooling (`make lint`); `lint project` retired entirely and `rules sync` retired into `adapters sync` (codex re-materialization runs there). The guest-owned predicate (`guest::owned`) and every native workflow-verb handler are deleted.
- **One help source of truth.** The full operator grammar — provisioning verbs included — lives in `specify-dispatch`; the guest serves `--help` / `--version` / usage errors for everything (argv[0] pinned to `specify` in the guest parse so help renders the real binary name), while the provisioning verbs' *execution* is native-only: the guest router refuses them with the typed `unsupported` pointing back at the native binary.
- **In-guest adapter resolution.** Forwarded verbs resolve adapters inside the guest: the generated manifest mounts the global store **read-only** at `/specify-store` (the wasm32 `adapter_store_root`), and the guest shim registers a describe runner that routes the resolver's describe dispatch through the deployment's WIT `source` / `target` imports by adapter id. The no-fetch / no-store-write fence is untouched — the mount is read-only and hydration stays native; store misses keep their typed errors.
- **`--plan-dir` narrows at the seam.** A forwarded verb naming a plan root other than the working directory is refused (`argument`, exit 2) — the guest anchors plan artifacts at the `"."` preopen, so any other plan root would be silently ignored.

## Operator onboarding (RFC-65 §"Operator onboarding")

**Decision (2026-07).** `specify init` gains the RFC-65 elicitation veneer, strictly *above* the hydration kernel — flags are the substrate, and nothing at or below hydration, manifest generation, or scaffolding can prompt.

- **Typed missing-flag errors off a TTY.** Every init input is suppliable as a flag. A missing `<adapter>` (without `--workspace` / `--upgrade`) when stdin is not a TTY is the typed `init-adapter-required` (`Error::Validation`, exit 2) naming the positional and both alternatives; the clap `required_unless_present_any` constraint was lifted so the argv reaches the handler. A missing required `--platforms` keeps the existing typed `project-platforms-required` naming the flag and the target's default set.
- **TTY prompt mode.** When stdin is a TTY and a required argument is missing, the handler prompts (hand-rolled line prompts over `std::io`, labels on stderr): the adapter up front, and `--platforms` reactively — the idempotent scaffold re-runs once after catching `project-platforms-required`, since only the resolved target adapter can declare the requirement. Flags always win; prompts fill only the gaps, and a prompted run's report carries the `equivalent` fully-flagged invocation to teach the non-interactive form.
- **Idempotent re-entry.** `specify init` over a project whose `.specify/project.yaml` exists changes nothing and exits 0 with a re-entry body (`already-initialized: true`, the recorded identity, and the literal `specify init --upgrade`); workspace init keeps its typed refusal. Rerunning the door is never an error.
- **Postflight report.** The init envelope gains `hydrated` (the resolved pinned set, `<name>@<version>`, bootstrap order), `adapter-store` (the resolved store root), and `next` (the literal next command, mirrored by the text renderer's `Next:` line).

## In-process host mount (RFC-65 move 2, amending D-bin)

**Decision (2026-07).** The forwarded leg runs the macro-generated command-mode runtime **in-process** — no subprocess, no second binary (operator decision, YAGNI). `omnia::runtime!` now generates a public sync `drive(builder: DeploymentBuilder) -> Result<ExitStatus>` beside `main` (re-exported as `pub use runtime::{drive, main};`), so a binary with its own verb surface mounts command mode without being the generated `main`. `specify-runtime` hosts the macro invocation as its `host` module (`crates/runtime/src/host.rs` — `mode: command`, the cursor-bound backends), and `specify_runtime::drive` keeps its signature but calls `host::drive` directly, mapping the returned `ExitStatus` low byte onto process passthrough. The macro stays the single source of the host wiring — nothing hand-rolls `Backends` / `Wiring` in Specify (the test-only bundles in `crates/runtime/tests/common.rs` mirror it for stubbed backends, unchanged).

- **What died.** The `specify-host` binary target, its beside-the-executable resolution (`HOST_BINARY` / `host_binary()`), the test-side `ensure_host_binary()` self-builds, and the two-binary release layout (`docs/release.md`'s pending "package `specify-host`" item resolves by deletion). The replay sibling (`specify-runtime-replay`) is untouched.
- **Failure surface moves onto the envelope.** Failures ahead of the guest run — deployment assembly (`building runtime: …`), backend connect (`cursor-agent` missing from `PATH`) — previously landed on the spawned host's own stderr with exit 1; they now return as `anyhow` errors from `drive` and render through the existing `guest-runtime-failed` envelope (exit 1) with the full context chain (`{err:#}`), so the operator-visible text is preserved inside a well-formed envelope. Guest exits still pass through verbatim; the exit-code contract (usage 2, version-too-old 3, guest passthrough) and JSON envelopes are unchanged.
- **The bare host form is gone.** Debugging and Omnia-native deployments use the `specify-runtime-replay` binary or omnia's own CLI over the same manifest; the operational cursor-bound runtime is reachable only through `specify`.

## Core versioned by the binary (RFC-65 move 4, amending D-dist)

**Decision (2026-07).** The workflow (core) guest is **resolved by the binary's own version**, not embedded: the identity is `specify:core@<CARGO_PKG_VERSION>` — the binary version *is* the core version, one knob, no pin surface for a project to drift on. The committed `crates/workflow-guest/guest.wasm`, its `.sha256` sidecar, the `tests/dist.rs` staleness gate, the `cargo make dist-guest` task, and the `include_bytes!` payload (`specify_runtime::WORKFLOW_GUEST_WASM`) are all deleted; guest-reachable code changes need no regeneration step anymore. The `publish-core` release leg (RFC-66) stops being inert — a released binary consumes exactly the identity its tag published, and the `needs: [build, publish-core]` lockstep guarantees the pair ships together.

- **Resolution order (`src/runtime/commands/deploy.rs::resolve_core`).** (1) The **development override** — the `SPECIFY_CORE_PATH` env var (a set-but-dangling path is the typed `core-override-missing`, never a silent fall-through), then the in-repo dev build at `target/wasm32-wasip2/{release,debug}/specify_workflow_guest.wasm` under the project dir — trusted as-is, the same posture as a bare-name adapter; development only, a released binary in a consumer project misses both probes. (2) The **global store entry** `core@<binary version>.wasm`, through the same verification pair every pinned adapter passes (RFC-48 D4 verify-on-read plus the committed-lock gate). A miss on both at drive time is the typed `adapter-not-installed` naming `core@<version>` and the literal `specify adapters sync` — the drive never fetches.
- **Hydration.** `specify init` and `specify adapters sync` prepend `specify:core@<binary version>` to the hydration set when no development override resolves, so the core pulls through the existing native kernel (`hydrate::hydrate` + `install_tofu`) and pins into `.specify/adapters.lock` like any adapter. The kernel itself stays version-agnostic — only the binary's provisioning triggers know the binary version and the override state — and the guest-never-fetches fence is untouched.
- **Tests self-build the dev core.** The integration suites pin `SPECIFY_CORE_PATH` to a once-per-process debug build of `specify-workflow-guest` (`tests/common.rs::workflow_guest_wasm`), so `cargo make ci` is self-contained and never pulls `specify:core`; the store and miss legs are covered by staging entries into the isolated store root.
- **The embed option stays open.** When Omnia's generic `runtime!` embed lands, opting in removes hydration and the manifest's core entry without touching the generator (`deploy::generate` takes the core as a plain path) — the RFC's two interchangeable modes.
